# ClamAVの最後の正常な過去世代を保護する設計

専用保存先の世代公開と所有者向け整理CLIに実装済み。変更前の基準は `e46fa06`。
[合成保存先での検証記録](acceptance/clamav-previous-generation-protection-2026-11-19.json)を参照。

## 現状と保護する条件

更新は候補のCVDと署名確認記録を配置・同期した後、`current.json` を置き換える。切替より前に止まると、検証済みでも一度も公開されていない世代が残る。整理CLIは、現行以下の版・ファイル構成・ヘッダーと、現行との内容差を見て過去世代を数える。候補の全体ハッシュは計算するが、公開時の記録とは照合しない。このため、後続の正常更新で現行の版が進むと、未公開世代が本物の過去世代の代わりに数えられる。ヘッダー以降の破損も同様に数えられ得る。[現行の公開処理](../pc_scanner/signature_update.py#L453)／[現行の整理判定](../pc_scanner/signature_maintenance.py#L188)／[確認記録](acceptance/vulnerability-check-2026-11-18.json)

現行と使用中の世代に加え、**直前から順に調べて、公開履歴と内容の双方を確認できた最も新しい過去世代**を保護する。より新しい過去世代の状態が未確認なら、候補を飛ばして保護を確定せず、世代削除を保留する。実際の公開とCVDの完全性が対象で、分離署名による作成日時の確認や鮮度の判定とは別に扱う。例えば、以前 `partial`／`stale` と表示されても、当時の公開検証を通過し、現在も公開時の内容と一致する世代は保護対象になり得る。

所有者と私有保存先は現行どおりの信頼境界とする。ハッシュは保存後の破損や取り違えを検出する。同じアカウントで動くプロセスがCVDと記録の両方を改変する場合の防御は、この方式の保証に含めない。[セキュリティ方針](../SECURITY.md)／[定義更新の設計](clamav-signature-update-design.md)

## 公開履歴の記録方法

`current.json` の新形式（例 `schema: 2`）を公開の正本とする。現在の `generation`、`content`、`versions` を維持し、直前を先頭にした `previous` と、移行前に存在した公開未確認IDの `legacy_untracked` を加える。`previous` の各要素は `generation`、公開時の `content`、3ファイルの `versions` を持つ。旧形式の現行を移行する際は、その旧 `current.json` が持つ内容と版を使う。既存の世代別 `.verification.json` は、引き続き分離署名の確認結果を担う。

| 方法 | 採否と理由 |
| --- | --- |
| 世代別記録とのハッシュ照合だけを加える | 破損は判別できるが、切替前に配置された世代にも記録があるため、公開の有無は区別できない。 |
| 公開ログを別ファイルへ追記する | 長期監査には使えるが、ログと現行参照の間で停止した場合の復旧規則が増える。 |
| 現行参照と保護に必要な公開履歴を一緒に置き換える | 採用。切替の成否を1ファイルで判断でき、容量に合わせて有限の記録で運用できる。 |

内容が変わる更新では、版番号が同じ場合も、更新ロック下で現在の参照と実CVDを照合し、その参照を新しい `previous` の先頭に加える。候補の配置・同期後、公開ロック下で新しい現行参照と履歴を既存の永続書込み手順でまとめて置き換える。配置後・置換前の停止では、旧参照と旧履歴が残り、候補は公開履歴に入らない。置換後・応答前の失敗は既存の `unknown` として報告する。次回は実際に残った参照を読み、候補やログから補完しない。`unchanged` では世代IDと公開履歴を維持し、分離署名の証跡だけを更新できる。

4枠の保存上限を維持し、ディレクトリ名・世代ID・一覧件数とJSONサイズの既存の制約を使う。JSONは既知の形式・キー・型に限り、重複キー、重複ID、現行IDの混入、3つの定義名と整数版の組に合わない記録、未知の形式は拒否する。所有者CLIが対象世代と関連記録・leaseの削除を完了して同期できた後、そのIDだけを公開ロック下で履歴から除く。履歴の更新に失敗した場合はIDを残す。次の公開時の整理は、正常と確認できた保護世代より古く、世代・関連記録・leaseの不在をすべて確定できたIDだけに限る。読み取りに失敗したIDや、現在の保護の判断に必要な直前の欠損は、容量の都合で履歴から捨てない。上限内に収められない場合は公開を保留する。独立した長期監査ログの用途には使わない。

## 照合と削除保留

一覧と削除で共通の判定を使う。公開順は履歴から取得し、版や更新日時は順序の根拠に使わない。検証は、既存の私有権限・クラウド未取得ファイル除外・リンク拒否・容量制限を保ち、3つのCVD全体から現在と同じ方式でSHA-256を算出する。計算した `content` と `versions` が公開履歴の両方に一致する場合にだけ正常とみなす。現行と内容が同じ複製は、独立した過去世代の代わりに数えない。

| 判定 | 過去世代の保護と削除の扱い |
| --- | --- |
| 公開済みで内容・版が一致 | 公開順で最も新しい正常な過去世代を `last_previous` とする。 |
| 公開済みだが破損が確定 | 一致しないハッシュ・版、または安定して読めた不正形式は候補から除く。正常なさらに古い世代を探す。対象の削除は正常な過去世代を別に確認でき、既存の私有権限・構造・revision条件も満たす場合だけ許可する。 |
| 公開履歴にない新形式の孤立世代 | 候補から除く。正常な過去世代を保護できる場合、または履歴が健全で「まだ一度も切替がない」と確定できる場合に限り、既存条件を満たすものを選択整理できる。 |
| 公開記録がない旧世代 | `legacy_untracked` として候補から除く。ディレクトリや署名確認記録だけで公開済みとは認定しない。移行時の旧現行より前か未公開の世代なので、記録と一致する過去世代を保護できる場合だけ選択整理でき、整理後は履歴から除く。保護を確定できない間は削除を保留する（2026-11-19のレビューで変更）。 |
| 読み取り失敗、権限・メタデータ確認失敗、期限超過、読み取り中の変更 | `unavailable` とし、破損確定と区別する。保護する世代の確定に必要な範囲または選択対象で発生した場合、世代削除を保留する。安定した不一致が得られる前の短い読み取りもこの扱いとする。 |
| 公開履歴の欠損・破損、または正常な過去世代を確認できない | 世代削除を保留し、理由を一覧に表示する。正常な初回公開で履歴が空の場合だけ、「保護すべき過去世代はまだない」と判断できる。 |

確定した不一致と一時的な失敗を分けるため、既存の `digest_directory()` が返す一般的な `OSError` だけで分類しない。安定した読み取りから得た形式エラーや一致しない結果と、I/Oや状態確認の失敗を、構造化した結果か別の例外に分ける。確定できない場合は保留側に倒す。stage の容量計上・保護と配布元の復旧は既存の規則を使い、破損した公開履歴からstageを昇格しない。

削除は所有者CLIの選択操作に限る。`list` の確認用revisionは対象のファイル・世代別記録に加え、公開履歴と保護判定に依存する世代のID・検証結果も含める。`delete` は更新ロック下で現行の内容、公開履歴、保護判定とrevisionを再検証する。選択対象に既存のleaseがあれば排他を取得する。最初の `unlink` の前に参照と検証したファイルの同一性を再確認する。比較とハッシュ計算は短い公開ロックの外で行い、現行世代の共有leaseを維持する。削除後に履歴を整理する場合は選択対象のleaseを閉じてから公開ロックを取得し、既存のロック順序を守る。I/O失敗や期限超過が削除の開始前なら何も消さない。削除開始後のI/O失敗は残存物と記録を再一覧で確認できるよう報告する。

世代ディレクトリの削除が済み、その後の処理を確認できない場合は、`partial` に `deleted`、`directory_synced`、`lease_removed`、`history_updated` を含める。leaseファイルの除去後に親ディレクトリを同期し、除去に失敗した場合も同期を試みる。leaseの後片付けと同期を確認してから履歴を更新する。同期に失敗した場合、`deleted` は実行時にディレクトリが消えたことを示す。`history_updated: false` は履歴更新が確認できないことを示し、参照の置換後に同期や読戻しが失敗した場合も含む。整理する履歴がなければ `history_updated` は `null` とする。stageの削除で同期を確認できない場合も、`partial` に `deleted` と `directory_synced: false` を含める。残った履歴の記録は、世代・検証記録・leaseがすべて無く、記録と一致する過去世代を保護できるときに後の公開の整理で除かれ、それまでは世代削除が保留されることがある。leaseの除去に失敗すると、残ったleaseは一覧に出ず、後の公開でも記録が除かれないので、所有者が手で消す。検査が新規にleaseを取るのは現行世代だけなので、削除済みの世代のleaseは使われない（`fd73200` のレビューで追記）。

leaseがない過去世代は更新ロックで保護する。検査が新規にleaseを取得するのは現行世代だけで、更新ロックが整理中の現行参照の切替を防ぐ。

## 旧形式の扱いと導入手順

1. 新しい読み取り処理は、厳密に検証した旧 `current.json` も受け付ける。既存の検査・更新・復旧を維持する。一覧と削除は、移行までは以前の版の規則で判定する。先頭部分とサイズが正しく、版が現行以下で、内容が現行と異なる世代を戻し先とし、それが1つだけなら保護する。読み取れない世代があれば世代削除を保留する。旧形式のファイルを書き換えるための読み取り操作は設けない。
2. 最初の**内容が変わる正常な公開**で新形式へ移行する。更新ロック下で移行開始時のIDを取得し、旧形式の現行だけを照合済みの公開済み世代として `previous` に引き継ぐ。それ以外の既存IDは `legacy_untracked` に記録する。初回候補の配置が終わってから移行対象を列挙すると候補を誤分類するため、配置前に取得する。参照が一度もない保存先の初回公開は移行ではないため、既存IDを記録しない。初回の切替の失敗で残った世代は一度も公開されておらず、記録すると保護すべき過去世代がないまま保留され続け、3つ残ると4枠が埋まって更新が恒久的に止まった（2026-11-20の脆弱性チェックで再現）。これらは上表の孤立世代として、履歴が空の初回公開の後に選択整理できる。参照を失った保存先とは区別できないため、その場合の既存世代も同じ扱いになる（以前の版と同じ）。
3. 移行前に4枠に達していても、1の規則で戻し先を1つ残したまま所有者が選択整理し、移行の更新に必要な空きを作れる。当初は未確認の旧世代を一切削除しない案だったが、以前の版で4枠に達した保存先も、古い世代を2つ以上残した保存先も、移行の前後で更新が恒久的に止まることを2026-11-19のレビューで再現したため改めた。移行後の `legacy_untracked` は上表のとおり扱う。強制削除や待機期限の短縮は導入しない。
4. 新形式を理解しない旧バイナリを同じ保存先へ戻すと、現行の厳密なキー検査で参照を受け付けない。導入時に共有するCLI・MCPを揃え、新形式の参照を旧形式に手で書き戻す運用は採用しない。

## 実装と受入の確認項目

| ケース | 期待結果 |
| --- | --- |
| Aを公開済み、Bを配置後に切替前で停止、後からCを公開 | BがC以下の版でも過去世代に数えず、Aの削除を拒否する。 |
| 公開済み過去世代のヘッダー以降を破損 | 保存済みハッシュとの差で候補除外。さらに古い正常世代があればそれを保護し、なければ世代削除を保留する。 |
| 旧形式、記録のない旧世代、最初の正常切替 | 検査・更新が継続し、旧現行だけが履歴に入る。満杯でも以前の規則で戻し先を1つ残して整理でき、移行後は記録と一致する過去世代を保護できれば旧世代を整理できる。保護を確定できなければ保留理由を出す。 |
| `EIO`、期限超過、読取り中の差替え、参照の不正 | 異常が保護判定に関わる削除は保留。事前の失敗で対象・記録・待機情報が変更されない。 |
| `unchanged`、置換前後の失敗、古いrevision、使用中lease | 同一内容で履歴を増やさず、置換後は永続参照を基準に再判断する。古いrevision・現行・使用中の対象を削除しない。 |
| 保護すべき世代が確定し、別の安全な対象を選択 | 選択した1件だけを整理でき、保護世代・現行・待機情報が維持される。 |

最初に合成保存先で公開境界と各エラーを試験し、Android・MCP関連を含む全テストで既存の契約を確認する。次に必要に応じて、実CVDを使う独立した試験保存先で4枠時の一覧・削除の所要時間を測り、既存の30秒制限と、検証中も現行の検査を開始できることを確かめる。
