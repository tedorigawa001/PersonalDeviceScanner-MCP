# Android 対応（第1段階）の設計

所有者自身の Android 端末を PC に USB でつなぎ、ADB（Android Debug Bridge）で**読み取り専用**に点検する。
既存の方針（固定の操作だけ・読み取り専用・端末から来る文字列は信用しない・「安全」とは判定しない）をそのまま当てはめる。

状態：第1段階を実装済み（2026-10-14、`pc_scanner/android.py`）。当初の「要確認」3点は Android エミュレーター
（Android 10 と 16）で確かめて反映した（[記録](acceptance/android-emulator-2026-10-14.json)）。実装後に同じエミュレーターで
通しで動かし、結果も同じ記録に残した。USB 接続での値など、実機でしか確かめられない点は「実機で確認」と書いた。

## 目的と範囲

**第1段階で確かめること**

| 項目 | 目的 |
|---|---|
| 端末の基本情報 | Android のバージョンとセキュリティパッチの日付。古いパッチは既知の脆弱性が残っている目安になる |
| アプリ | 一覧と、端末が記録している導入元（`installer`）。導入元は観測した値として返し、「サイドロード」とは断定しない。見せる一覧は既定で利用者が入れたもの（システムアプリ以外）に絞るが、照合には全パッケージを使う |
| 強い権限を持つアプリ | ユーザー補助（画面の読み取り・操作）、通知へのアクセス、端末管理。ストーカーウェアがよく悪用する |
| 既知の監視アプリとの照合 | パッケージ名を、公開されている指標（下の「照合データ」）と比べる。指標の分類（stalkerware／watchware）を保つ |

端末のユーザーごと（仕事用プロファイルを含む）に調べ、アプリは「ユーザー ID とパッケージ名」の組で扱う。

**第1段階で扱わないこと**

- SMS・通話履歴・連絡先・写真・ブラウザー履歴などの個人データ
- APK（アプリ本体）の取り出し。したがって署名証明書による照合も行わない（第2段階で検討）
- アプリの削除・無効化、設定の変更、端末への書き込み、root
- Wi-Fi 経由の ADB（`adb connect`・ワイヤレスデバッグ）。実際の接続方式を確かめ、USB と確認できない端末は点検しない（下の「接続方式の確認」）
- MVT / AndroidQF による詳細検査（第2段階で、所有者が選んで使う別の検査として検討）

## 前提と安全上の注意

- **USB デバッグを有効にする必要がある**。これは端末の攻撃面を増やす。README には「点検のときだけ有効にし、終わったら無効にして、
  開発者向けオプションの『USB デバッグの承認を取り消す』を行う」と書く。このツールが USB デバッグを有効・無効にすることはない。
- **本人の端末だけ**を対象にする。他人の端末を同意なく調べることは、このツールの用途ではない（MVT もライセンスで同意を条件にしている）。
  点検できる端末は、所有者が設定ファイルに書いたものだけ（下の「設定」）。
- ADB の承認は端末側で所有者が行う。未承認（`unauthorized`）なら、その旨を返して何もしない。
- `adb` は Google の Android SDK Platform-Tools を公式配布元から導入してもらう（同梱しない。ClamAV や osquery と同じ扱い）。
- 照合できるのは既知の監視アプリ（指標にあるもの）だけ。検出なしは安全の証明にならない。結果の警告と README に明記する。

## 設定

```toml
[android]
# Android SDK Platform-Tools の adb の絶対パス（PATH からは探さない）
adb_binary = "/absolute/path/to/platform-tools/adb"
# 所有者が取得した監視アプリの指標（STIX2）。下の「照合データ」を参照
indicators_file = "/absolute/path/to/stalkerware.stix2"
# 指標がこれより古いと partial（既定 30 日）
max_indicator_age_days = 30
# セキュリティパッチがこれより古いと所見にする（既定 90 日）
max_patch_age_days = 90

[android_devices]
# 「エイリアス = ADB のシリアル」（`adb devices -l` で確認）。AI はエイリアスでしか指定できない
my-phone = "SERIAL"
```

- AI が指定できるのは `[android_devices]` のエイリアスだけ。シリアルは結果に含めない（端末を識別できる情報のため）。
- シリアルの文字列からは接続方式を判断しない。ワイヤレスデバッグの端末は `ip:port` 形式だけでなく、`:` を含まない mDNS 名
  （`adb-…._adb-tls-connect._tcp` など）でも現れるため。USB かどうかは下の「接続方式の確認」で確かめる。
- 既存の「未知の設定の警告」（`SETTINGS`）に `android` と `android_devices` を加える。

## ADB で実行するコマンド（固定）

すべて固定の引数で実行する。`adb shell` は引数をつないで端末のシェルに渡すため、
**端末から得た文字列（パッケージ名など）を引数に入れない**。アプリごとのコマンド（`dumpsys package <名前>` など）は第1段階では使わない。
端末から得た値で引数に入れるのは、形式を確かめた数字（ユーザー ID と転送 ID）だけ。

### 接続方式の確認（USB に限る）

ADB の公式実装では、各接続は種類（USB か、TCP などのソケットか）を持つが、`adb devices -l` のテキスト出力には現れない。
種類が出るのはプロトコルバッファ形式の一覧（`connection_type` が `USB` か `SOCKET`）で、`adb track-devices --proto-text` で得られる。

1. `adb track-devices --proto-text` の最初の一覧から、設定したシリアルの端末を探す。
   `connection_type` が `USB` で、状態が `device` のときだけ続ける。見つからない・USB でない・`unauthorized` などは `error`。
2. その一覧にある転送 ID（`transport_id`、数字）を控え、以降のコマンドは `adb -t <転送ID> …` で実行する。
   確認した接続とは別の接続（同じ端末のワイヤレス接続など）に送らないため。途中でつなぎ直すと ID が変わり、コマンドは失敗する（`error`）。

**エミュレーターで確かめたこと**（Platform-Tools 37.0.1）：

- 出力は、4桁の16進数の長さに続くテキスト形式のプロトコルバッファ。各端末は次のように出る：
  `device { serial: "…" state: DEVICE product: "…" model: "…" device: "…" connection_type: SOCKET transport_id: 1 }`
- エミュレーターは `connection_type: SOCKET` になる（TCP で接続するため）。したがってこの設計ではエミュレーターも点検の対象外になる。
- **オプションは `--proto-text` だけを付ける**。adb は `track-devices` の直後の1つしか見ないため、`track-devices -l --proto-text`
  ではテキスト形式になり、接続方式が出ない。
- `track-devices` は終了しないので、既存の `run_bounded` では時間切れになる（3秒で確認）。最初の一覧（と、続く更新）を
  読んだら止める専用の読み取りが要る。
- ADB サーバーを起動した直後は、端末がまだ一覧にない、または `offline` のことがある（起動直後の `get-state` は
  `error: device offline` だった）。`track-devices` は変化があるたびに新しい一覧を送ってくるので、決めた時間（例：5秒）まで
  更新を待ち、設定した端末が `USB` かつ `DEVICE` になるのを確かめる。時間内にそうならなければ `error`。
- `adb get-devpath` はエミュレーターでは `unknown` だった。USB の判定には使わず、`connection_type` だけで判断する。
- `--proto-text` が使える最低の Platform-Tools の版は、公開のリリースノートにも変更履歴にも見当たらなかった。実行時に出力の形式を確かめ、
  プロトコルバッファの形式でなければ「Platform-Tools が古い」として `error` で案内する（README には確認した 37.0.1 以上を推奨と書く）。
- **実機で確認**：USB でつないだ端末が `connection_type: USB` になること（エミュレーターでは確かめられない）。

### 実行するコマンド

| 用途 | コマンド（`adb -t <転送ID> shell` に続く部分） | 取り出す内容 |
|---|---|---|
| 基本情報 | `getprop` | 決めたプロパティだけ：`ro.build.version.release`・`ro.build.version.sdk`・`ro.build.version.security_patch`・`ro.product.manufacturer`・`ro.product.model`。ほかは捨てる（`ro.serialno` などを返さない） |
| ユーザー | `pm list users` | 端末のユーザー（仕事用プロファイルを含む）の ID とフラグ（`UserInfo{ID:名前:フラグ}`） |
| ユーザーの種類と親 | `cmd user list -v` | Android 14 以降などでは種類（`profile.MANAGED` など）と親（`parentId=0`）が出る |
| アプリ（全パッケージ） | `pm list packages -i -U --show-versioncode --user <ID>` | パッケージ名・導入元（`installer=`）・UID・バージョンコード。システムアプリも含む |
| システムアプリ | `pm list packages -s --user <ID>` | システムアプリ（更新されたものを含む）のパッケージ名。全パッケージに `is_system` を付けるために使う |
| ランチャー活動 | `cmd package query-activities --brief --user <ID> -a android.intent.action.MAIN -c android.intent.category.LAUNCHER` | ランチャーに表示される活動（アクティビティ）を持つパッケージ |
| ユーザー補助 | `settings --user <ID> get secure enabled_accessibility_services` | 有効なサービス（`パッケージ/クラス` を `:` 区切り。なければ `null`）。通常のユーザーだけで取得する（仕事用プロファイルは親と共有。下を参照） |
| 通知へのアクセス | `settings --user <ID> get secure enabled_notification_listeners` | 同上 |
| 端末管理 | `dumpsys device_policy` | ユーザーごとの有効な端末管理アプリと、デバイスオーナー／プロファイルオーナー（MDM など） |

- **照合には全パッケージを使う**：`-3`（利用者が入れたアプリだけ）で絞ると、システムアプリとして入った監視アプリや、
  強い権限を持つシステムアプリが照合から漏れる。指標との照合と権限との突き合わせは全パッケージで行い、
  利用者に見せる一覧（`collect_android` の `apps`）だけを既定で `is_system` でないものに絞る。
- **ユーザーの指定をそろえる**：ユーザーごとの項目（アプリ・ランチャー活動・通知へのアクセス）は、すべて同じ
  `--user <ID>` で取得する。`dumpsys device_policy` は全ユーザー分を一度に出すので、ユーザーごとに分けて読む。
  照合はすべて「ユーザー ID とパッケージ名」の組で行い、別のユーザーのアプリ一覧と現在のユーザーの設定を突き合わせない。
  例外はユーザー補助で、仕事用プロファイルは親ユーザーの設定を共有するため、親ユーザーの値を親ユーザーのパッケージと突き合わせる（下を参照）。
- ユーザー ID は `pm list users` の結果から取るが、数字だけを受け付ける（端末からの文字列をそのまま渡さない）。
- **エミュレーターで確かめたこと**（Android 10・API 29 と Android 16・API 36、どちらも Google のサービスなしのイメージ）：
  - 上の表のコマンドは、両方の版で一般の ADB 権限のまま使えた（`--show-versioncode`・`-i`・`-U`・`-s`・`--user`、
    `cmd package query-activities --brief --user`、`settings --user`、`dumpsys device_policy`）。
    → **サポートする最低の版は Android 10 とする**（それより古い版は確かめていない）。
  - `pm list packages -i` の出力：`package:<名前> versionCode:<数字>  installer=<値> uid:<数字>`。事前導入のアプリは `installer=null`。
  - `cmd package query-activities --brief` の出力：`<N> activities found:` に続いて `Activity #<n>:` ごとに
    `パッケージ/クラス`（`com.android.calendar/.AllInOneActivity` のような短縮形を含む）の行。
  - `dumpsys device_policy` は `Enabled Device Admins (User <ID>, provisioningState: <n>):` の見出しでユーザーごとに分かれる
    （Android 16 では前に `Immutable state:` などが加わり、長さは約 3.5KB）。
  - 仕事用プロファイル（テスト用に作成）のパッケージ数は親ユーザーと違った（Android 16 で 181 対 168）。ユーザーごとの取得が必要。
- **ユーザー補助は仕事用プロファイルと親で共有される**（エミュレーターで確認）：
  - 仕事用プロファイルには `enabled_accessibility_services` の値がなく（`settings --user <ID> list secure` に出ない）、
    読むと親ユーザーの値が返った。親とプロファイルに別の値を書いても、プロファイルから読むと親の値だった（Android 10）。
  - したがって**ユーザー補助は、仕事用プロファイルでは取得せず、親ユーザーの値を親ユーザーのパッケージと突き合わせる**。
    プロファイルについては「親ユーザーの設定を共有する」と結果に記す。
  - 通知へのアクセスはユーザーごとに別の値を持った（両方の版で確認）。こちらは各ユーザーで取得し、そのユーザーのパッケージと突き合わせる。
  - 仕事用プロファイルとその親は、`cmd user list -v` の `type=profile.MANAGED` と `parentId=` で分かる（Android 16）。
    Android 10 では種類も親も出ず、`pm list users` のフラグ（16進数、`0x20` が MANAGED_PROFILE）だけが手がかりになる。
    親が明示されず、通常のユーザーが1人だけならそのユーザーを親とする。それ以外で親が分からなければ、そのプロファイルの
    ユーザー補助の扱いを「不明」として `partial` にする。
  - Android 16 では、存在しないサービスを書き込むと設定から取り除かれた（Android 10 では残った）。読み取りの処理はどちらの状態も扱う。
- **実機で確認**：メーカーによる出力の違い（とくに `dumpsys device_policy`）、MDM で作られた本物の仕事用プロファイルでの見え方。

### 観測した事実として返す（断定しない）

- **導入元**：`installer=` の値をそのまま返し、次のように分類する。どれも「どこから来たか」の推定であって、安全かどうかの判定ではない。

  | 分類 | `installer=` の値 | 意味 |
  |---|---|---|
  | `play_store` | `com.android.vending` | Google Play から導入 |
  | `package_installer` | `com.google.android.packageinstaller`・`com.android.packageinstaller` | 端末のインストーラー経由。APK ファイルから入れた可能性がある |
  | `other_installer` | 上記以外のパッケージ名 | 別のストアやアプリ経由（名前を返す） |
  | `unknown` | `null`・記載なし | 不明。ADB での導入、メーカーの事前導入、記録されていない場合などがあり、サイドロードとは限らない |

- **ランチャー活動**：`has_launcher_activity` として返す。ランチャー活動がないことは「アイコンを隠している」証拠ではない
  （キーボード・ウィジェット・プラグイン・常駐サービスなど、正規のアプリにも多い）。

### 取得できなかった項目の扱い

- 既存の `run_bounded` は、出力が上限を超えるとエンジンを止め、途中までの出力を返さずにエラーにする。この仕様のまま使い、
  **出力を切り詰めて結果に使うことはしない**。上限超過・時間切れ・コマンドの失敗・未対応は、その項目（とユーザー）を「取得できなかった」とする。
- **取得できなかった項目は「該当なし」として扱わない**。`data.unavailable` に項目・ユーザー ID・理由を並べ、`partial` にする。
  その項目に依存する判定は行わない（例：ランチャー活動を取得できなければ `has_launcher_activity` は `null` とし、ユーザー補助を
  取得できなければ、そのユーザーについて「強い権限を持つアプリはない」とは言わない）。
- **コマンドが成功しても、出力が想定した形でなければ「取得できなかった」とする**（実装時のレビューで追加）。例：
  `dumpsys device_policy` に端末管理の見出しが1つもない、あるユーザーの見出しがない、全パッケージの一覧に1件もない、
  システムアプリの一覧が空、ランチャーの出力に `… activities found` の見出しがない、`getprop` に決めたプロパティが1つもない。
  所有者の見出しがあるのに `admin=` の行がない場合も、読めなかった所有者として数える。
- 結果全体を `error` にするのは、接続方式の確認・ADB の起動・設定の誤りなど、どの項目も取得できない場合だけ。
  端末から1つも使える出力が得られなければ、`partial` ではなく `error` にする。

## 照合データ（stalkerware-indicators）

- 出典：Echap の [stalkerware-indicators](https://github.com/AssoEchap/stalkerware-indicators)。監視アプリのパッケージ名・署名証明書・
  接続先などを集めたもので、MVT なども使っている。ライセンスは CC-BY 4.0。
- **stalkerware と watchware の両方を含む**。watchware は子どもや従業員の見守りなどをうたう監視アプリで、本人や家族が承知のうえで
  入れていることもある。分類を落とさずに返す（下の「結果の形」）。
- **形式は STIX2（JSON）を使う**（`generated/stalkerware.stix2`）。YAML 版は標準ライブラリで読めず、依存が増えるため。
  2026-10-14 時点の構造（実ファイルで確認）：
  - `malware` オブジェクト 175 件。分類は `description` にあり、`Stalkerware application`（148）か `Watchware application`（27）。
  - `indicator` の `pattern` は `[app:id='…']`（パッケージ名、652 件：stalkerware 616・watchware 36）、`[app:cert.sha1='…']`、
    `[domain-name:value='…']`、`[file:hashes.sha256='…']` など。第1段階で使うのは `app:id` だけ。
  - `relationship`（`indicates`）が `indicator` から `malware` を指す。これをたどって、一致したパッケージ名の製品名と分類を得る。
  - ファイルは約 4.7MB。上限は余裕をもって設ける（例：32MB）。
- パターンは空白の有無を許して読み、`app:id` 以外や読めないものは使わない。`description` が上の2つ以外の `malware` は分類を
  `unknown` とし、その旨を警告する。
- **入手と更新は所有者が行う**（ClamAV の定義ファイルを `freshclam` で更新するのと同じ考え方）。このツール自体は指標をダウンロードしない
  （ネットワークへの接続を Wazuh 以外に増やさないため）。README に取得コマンドを載せる。
- 読み込み時に、ファイルの SHA-256・分類ごとの件数と、次の2つの日時を分けて記録し、結果の `data.indicators` に入れる。

  | 日時 | 値 | 使い方 |
  |---|---|---|
  | `generated_at`（指標の更新日時） | STIX2 の `indicator` の `modified` のうち最も新しいもの | **鮮度の判定に使う** |
  | `retrieved_at`（取得日時） | ファイルの更新日時（mtime） | 表示だけ。鮮度の判定には使わない |

  根拠：提供元はファイル全体を生成し直しており、2026-10-14 に確認した版では全 12,333 オブジェクトの `created`・`modified` が
  同じ数秒の間（2026-10-09 15:13:08〜12Z）にあり、生成したファイルのコミット時刻（15:13:13Z）と一致した。つまりこの値は
  提供元が指標を生成した日時で、古い版を後からダウンロードし直しても古いままになる。mtime は取得し直すと新しくなるため、
  鮮度の判定に使うと古い指標が通ってしまう。
- 鮮度の判定（経過時間は `generated_at` から PC の現在時刻（UTC）まで）：
  - `max_indicator_age_days` を**超えたら**古いとして `partial` と警告。ちょうど同じなら古くない
    （ClamAV の定義ファイルと同じ扱い。表示する日数は 0.1 日単位で切り上げ、上限以下に見えて実は超えている、を避ける）。
  - `modified` がない・日時として読めない `indicator` があれば、`generated_at` は求めずに鮮度を「不明」とし、`partial` と警告。
  - `generated_at` が現在より1日を超えて未来なら、日時が不正として鮮度を「不明」とし、`partial` と警告（新しいとはみなさない）。
    1日以内の未来は時計のずれとして経過0日とする。
  - 提供元がしばらく更新していない場合も古いと判定される。そのときの警告には「提供元が更新していない可能性もある」と添える。
- ファイルが読めない、`app:id` が0件のときも `partial` と警告。
- ファイルは信用できない入力として扱う：サイズの上限、JSON の構造の確認、名前の無害化（既存の `clean_text`）。
  ID・参照・パターン・名前・分類の型を確かめ、型が想定と違うオブジェクトは使わずに件数を警告する（`partial`）。
  ファイルがどんな内容でも、指標を読めないだけで端末の点検は続け、`partial` を返す。
- 帰属表示：結果の `data.indicators.source` と README に「Echap stalkerware-indicators（CC-BY 4.0）」を記す。指標を同梱しないため、
  第三者表示（`THIRD_PARTY_NOTICES.md`）への追加は不要の見込み（同梱を検討する場合は改めて判断する）。

## 結果の形

既存と同じ形（`schema_version`・`source`・`status`・`findings`・`warnings`・`data`）。`source` は `adb`。

**所見（`findings`）の種類**

| `kind` | 深刻度 | 条件 |
|---|---|---|
| `monitoring_app_indicator` | high（stalkerware）／medium（watchware・unknown） | パッケージ名が指標と一致（システムアプリを含む全パッケージが対象）。指標の製品名と分類（`category`）を添える |
| `review` | medium | システムアプリでなく、導入元が `play_store` 以外（`package_installer`・`other_installer`・`unknown`）のアプリが、ユーザー補助・通知へのアクセス・端末管理のいずれかを持つ |
| `outdated_patch` | medium | セキュリティパッチが `max_patch_age_days` より古い |

- 所見はユーザー ID とパッケージ名の組で示す。
- `monitoring_app_indicator` の文言は「既知の監視アプリの指標と一致」とし、watchware には「見守りなどの目的で本人や家族が入れた可能性もある。
  入れた覚えがあるか確認を」と添える。
- `review` は「確認を勧める」であって、悪意の判定ではない。正規の MDM・支援技術アプリ・業務アプリもここに入りうる、と警告に書く。
  導入元の分類とランチャー活動の有無は、判断材料の事実として所見に添える（それ自体で深刻度を上げない）。
- 導入元だけ・ランチャー活動がないことだけでは所見にしない。アプリ一覧（`collect_android` の `apps`）の事実として返す。
- 強い権限を持つシステムアプリは `review` にしない（システムアプリの導入元はたいてい不明のため、ほぼすべてが該当してしまう）。
  `collect_android` の `privileged_access` に、`is_system` を付けた事実として示す。
- デバイスオーナー／プロファイルオーナーがいれば `data` に示し、「勤務先などの管理下にある可能性」を添える。

**`partial` になる場合**：指標が古い・読めない・分類の分からないものがある、取得できなかった項目がある（`data.unavailable`）、
見えないユーザー（プロファイル）があった、など。`error` は未設定・未接続・未承認・USB と確認できない・時間切れなど、どの項目も取得できない場合。

**返さない情報**：シリアル番号、アカウント、電話番号、アプリのデータ。パッケージ名とアプリのバージョンは点検に必要なため返す
（クラウドの AI に渡すと送信される点は、既存のプライバシーの注意と同じ）。

## 実装上の注意

- `adb` は既存の `run_bounded`（シェルを使わない起動・時間制限・出力上限・キャンセル・プロセスツリーの停止）で実行する。
  渡す環境変数は既存の許可リストのまま。`HOME`（Windows は `USERPROFILE`）が渡るので、所有者の既存の承認鍵（`~/.android/adbkey`）が使われる。
- **ADB サーバーの扱い**（macOS のエミュレーターで、既存の `run_bounded` を通して確認）：
  - サーバーが動いていないとき、`adb` は自分でサーバー（localhost:5037）を起動する。サーバーはエンジンのプロセスグループから離れ、
    `run_bounded` の停止処理でも止まらず、出力も開いたままにしないため、既存の「グループを抜けた子プロセス」の検出には当たらなかった。
    呼び出しの後もサーバーは動き続ける（adb の通常の動き）。
  - 起動した直後の最初のコマンドは `error: device offline` になった。上の「接続方式の確認」で、端末が使えるようになるまで待つ。
  - サーバーは他のツール（Android Studio など）と共有されるため、このツールからは止めない（`adb kill-server` しない）。
  - adb はポート 5037 で応答する相手を信用する（adb 自体の設計）。複数の人が使う PC では、先に偽のサーバーを起動されると
    偽の結果を返されうる。README の制限事項に書き、自分の PC での利用か、点検前に自分でサーバーを起動し直すことを勧める。
    止めたいときの方法（`adb kill-server`）を README に書く。
  - **Windows で確認**：エンジンを入れる Job Object にサーバーまで入ると、Job を閉じたときにサーバーが止まり、毎回起動し直して
    `device offline` の待ちが増えるおそれがある。Windows の実機で確かめ、必要ならサーバーを Job の外で起動する手順を加える。
- **パッケージ名とコンポーネント名は別々に確かめる**。ユーザー補助・通知へのアクセスの設定値や `dumpsys device_policy` の
  `ComponentInfo{…}` は「パッケージ/クラス」の形のコンポーネント名で、クラスは `.AccessibilityService` のような短縮形や、
  内部クラスの `$` を含むことがある。
  1. 最初の `/` でパッケージとクラスに分ける。
  2. クラスが `.` で始まる短縮形なら、パッケージ名を前に付けて展開する。
  3. パッケージ名は Android の規則（`.` で区切った各部分が英字で始まり、英数字と `_` だけ）で確かめる。
     クラス名は Java のクラス名の規則（各部分が英字・`_`・`$` で始まり、英数字・`_`・`$` が続く）で確かめる。
  4. 権限との突き合わせにはパッケージ名を使う。クラス名は表示用（無害化して返す）。
  - クラス名が規則に合わないだけなら、**コンポーネントを捨てない**（捨てると強い権限を持つアプリを見落とす）。パッケージに
    結び付けたまま、警告を付けて `partial` にする。パッケージ名が規則に合わず結び付けられないものは、無害化して
    `data.unattributed_components` に並べ、`partial` にする。
  - `pm list packages` のパッケージ名も同じ規則で確かめ、合わないものは無害化して示し、`partial` にする。
- 端末の時計がずれているとパッチの古さの判定が狂うため、比較には PC の日付を使う。

## テスト

- 実機の出力を基にした**合成の**出力（個人情報を含まない）で、各コマンドの解析・境界値・壊れた出力を確かめる。
  Android のバージョンやメーカーの違いを複数用意する。とくに次を確かめる：
  - 接続方式：`SOCKET` の端末や、`:` を含まない mDNS 名のワイヤレス端末を拒否し、`USB` だけを点検すること。以降のコマンドが
    確認した転送 ID で実行されること
  - ユーザー：仕事用プロファイルがある場合に、ユーザー補助を除く各項目が同じユーザー ID で取得され、別ユーザーの設定と突き合わせないこと。
    例外として、仕事用プロファイルのユーザー補助は親ユーザーの設定を使い、親ユーザーのパッケージ一覧と突き合わせること。
    結果に「親ユーザーの設定を共有する」と示し、親ユーザーが分からない場合は「不明」として `partial` にすること
  - 指標：stalkerware と watchware の分類が結果に残ること、分類の分からないものが `unknown` と警告になること
  - 導入元：`installer=null` を `unknown` とし、サイドロードと断定しないこと。ランチャー活動がないことだけで所見にしないこと
  - システムアプリ：システムアプリとして入った監視アプリが指標と一致し、強い権限を持つシステムアプリが権限の一覧に出ること
  - コンポーネント名：`.AccessibilityService` のような短縮形の展開、`$` を含む内部クラス、規則に合わないクラス名でも
    パッケージに結び付けて残すこと、パッケージ名が不正なものが `data.unattributed_components` に入ること
  - 指標の鮮度：`modified` から求めること（ファイルの mtime を新しくしても古い指標は古いままであること）、期限ちょうどは
    古くないこと、超えたら古いこと、`modified` の欠落と1日を超える未来が「不明」になること
  - 取得できなかった項目：出力の上限超過・失敗・未対応が `data.unavailable` に入り、「該当なし」として扱われないこと
- テスト用の偽の `adb`（決まった出力を返すスクリプト）で、`run_bounded` を通した呼び出し・時間切れ・キャンセルを確かめる。
- 照合データは小さな合成の STIX2 で確かめる（実際の指標はテストに入れない）。
- 受入試験：所有者の実機で行い、記録は端末名・シリアル・アプリ一覧を伏せて `docs/acceptance/` に残す。
- 将来の検討：CI で Android エミュレーターを動かす（重いため第1段階では行わない）。
