# 個人PCの外向き通信の観測（第1段階）の設計

状態：第1段階を実装（2026-10-29、2026-10-30のレビューを反映）。2026-10-30にmacOSの実接続・ブラウザーの部分受入を追加。
未接続UDPの正規化は同日に修正・macOS再受入済み。権限差、Windows/Linuxの実環境は未確認・残課題。

## 目的と第1段階の範囲

このPC上のプロセスと接続先を、OSが公開するソケット情報から読み取り専用で確認する。
CLI・MCPで時間を区切って観測し、保存を許可した結果を静的ダッシュボードで確認する。
[家庭LAN検出](lan-discovery-design.md)とは別機能であり、他機器の通信は収集しない。
待受ソケットは既存の`inventory`の`listening_ports`（PID・プロセス名・ローカルのアドレスとportを、提供許可なしにMCPへ返す）に残し、
本機能はリモートアドレスのある接続だけを扱う。接続先は利用サービスを示しうるため、こちらだけを別の提供許可の対象にする。

第1段階は接続一覧の定期読み取りで、パケットキャプチャ、通信本文・TLS鍵の取得、TLS復号、DNS問い合わせの傍受を行わない。
逆引き・接続先への問い合わせ・外部脅威情報照合も行わない。プロセスの停止、通信遮断、設定変更、権限昇格、常駐サービスの導入は対象外。
自動的な悪性判定・深刻度付与はせず、既存のClamAV・Wazuhの所見を置き換えない。

**ソケット一覧は「外向きに送信されたパケット」の証拠ではない。** リモートアドレスのある接続を候補として観測する。
接続開始方向は原則`unknown`とし、受信した接続も含みうる。TCPの接続状態から送信実績を推定しない。
ポーリングの間に開始・終了した短命な接続、OSが隠す他ユーザーのプロセス、未接続UDPの送信先は見逃す。
通信量・送信回数・送信内容・全通信の網羅性は返さず、0件でも「通信なし」「感染なし」としない。

## 許可と設定案

既定で無効。所有者の設定だけで観測時間・件数上限とMCP提供を決める。AIが任意のPID・パス・コマンド・接続先を指定する入口を作らない。

```toml
# 実装済み。既定では無効。所有者が設定する。
[outbound_connections]
enabled = false
duration_seconds = 10             # 1..60秒。観測窓
interval_seconds = 1              # 1..10秒、duration以下
max_connections = 2000            # 1..2000。統合後の上限（正規化結果2MiBに収まる値）
expose_identifiers_to_mcp = false  # プロセス名・PID・接続先IP/port等をAIへ提供
save_details = false              # 接続先を含む詳細を履歴に保存（history.details=trueも必要）
```

- CLIのローカル利用とMCPへの提供許可を分離する。MCP提供が無効なら収集前に拒否し、
  エラー・進捗・ツール状態にも識別情報を含めない。MCPの引数で許可設定や時間上限を上書きしない。
- IP・port・プロセス名にも利用サービス等の私的情報が含まれる。MCP応答が利用するAIサービスへ渡る可能性を設定の説明に明記する。
- 詳細の保存は`history.details=true`に加えて`save_details=true`を必要とする。マルウェア検査等のために詳細保存を
  有効にした所有者が、プロセスごとの接続先（利用したサービスの記録に相当する）を新たな判断なしに保存し始めないようにする。
- 実行ユーザーにOSが公開する範囲だけを読む。管理者権限を要求せず、見えない項目を推測しない。
  必要な権限がない場合はその制約を示す。ユーザー名、コマンドライン、環境変数、実行ファイルの内容・完全パスは収集しない。
- この操作にはエンジン更新確認などの外部API照会を適用しない。収集コマンドの名前解決を無効にする。

## 収集方式とOS別の採用条件

共通の観測・正規化・集約を`pc_scanner/connections.py`（案）へ置き、OS別の読み取りを分離する。
既存の固定osqueryクエリ実行・時間上限・取消の基盤を再利用する。
第一候補は`process_open_sockets`と`processes`の固定クエリによる数値アドレス・port・PID・プロセス名の取得。
OS・osqueryの版ごとに列と取得範囲を試作確認してから採否を決め、未対応の列を無条件に要求するJOINは使わない。
依存やバックエンドを追加する場合は、ロック・SBOM・第三者表示を既存の全プロファイルに反映する。

| OS | 読み取りの代替候補と、実装前に確かめる点 |
|---|---|
| Windows | IP Helper APIのTCP/UDP所有PIDテーブル。IPv4/IPv6、プロセス名取得拒否、PID再利用、UDPの宛先欠落 |
| macOS | 数値出力の固定`lsof`等。一般ユーザーでの他プロセス可視性、機械可読出力、OSの権限制限 |
| Linux | procfs等のソケットとPID対応。hidepid、別ユーザー、network namespace・コンテナによる可視性制限 |

上記は実証済みの対応表ではなく採用候補。各OSで要件を満たす方式を1つ固定し、実行中に別方式へ黙って切り替えない。
osqueryの既存設定を使う場合も、任意SQLのMCP公開はしない。補助コマンドは所有者設定または検証済み絶対パス、固定引数配列、
shell不使用。数値出力を強制し、コマンドのエラー原文やプロセス一覧全文をログへ流さない。

- 全体の処理上限は観測窓+5秒。各読み取りは残り時間と最大2秒の小さい方まで。単調時計で期限を管理する。
  最初は直ちに読み、以降intervalごとに読み、読み取りが遅れた場合は遅延を記録して連続追いつき実行をしない。
- 1読み取りは出力2MiB・10000行、全体の読み取り出力は累計16MiB、正規化結果は2MiBまで。
  超過は切り詰めを明示してpartial。失敗した読み取りを成功した空一覧として扱わない。
- 生出力はメモリー内だけで処理し、一時ファイルやデバッグログに保存しない。子プロセスの出力も上限付きで読む。
- 子プロセス・ハンドルの停止と回収を時間上限・取消の管理下に置く。ブロックするAPIが停止要件を満たさなければ、
  終了できる子プロセスへ隔離するか未対応とする。終了後の遅延更新を認めない。
- 上限付きの実行器が取消・期限で子プロセスを止めた場合は、読み取りの失敗ではなく`cancelled`・`timeout`として扱う。
  読み取りの例外を一律に失敗や`network_changed`へ変えない（家庭LAN検出で2026-10-29に直した誤分類と同じ）。

## 接続の分類とプロセスの対応

IPv4/IPv6の数値アドレス、port 0..65535、TCP/UDP、状態を厳格に検証し、不明な形式を捨てた件数を理由別に示す。
ローカルアドレス一覧も同じ実行で読み、開始・終了と各読み取り時に変更を確認する。
対象はこの実行ホストのOS可視範囲であり、VPNの内側の宛先やVMの通信の見え方はOSに依存する。

| 分類 | 意味と表示 |
|---|---|
| `internet_candidate` | 特別用途でないグローバル宛先。インターネットへの実送信・到達を証明しない |
| `private_or_local` | RFC1918・ULA・リンクローカル等。LAN/VPN/仮想ネットワークのどれかは断定しない |
| `self_or_loopback` | 自分のアドレス・loopback。外部宛て一覧から除き、除外件数だけ表示 |
| `multicast_or_broadcast` | multicast・明確なbroadcast。別の件数として表示し、外部接続数に加算しない |
| `unknown` | 特別用途・判定情報不足。公開宛てに推測分類しない |

分類は固定した特別用途アドレスの規則・試験に基づき、Pythonの版による`is_global`の差だけで結果を変えない。
IPv4-mapped IPv6は分類時に正規化し、IPv6リンクローカルはscopeを保持する。未指定リモート・待受は外向き候補に数えない。
UDPのリモート不明は`destination_unavailable`の件数に残し、UDP未観測を0通信としない。
自己アドレス取得失敗は分類の制約を示してpartial。実行中の接続・アドレス変更は`network_changed`として中止し、既取得分をpartialで返す。
ルーティングを確認できない場合、出力に物理インターフェース名を推測して付けない。

PIDとプロセスの照合は可能なら生成時刻を含む。同じPIDの再利用は別プロセスとして扱う。
ソケットとプロセスを原子的に取得できない場合はその制約を示し、PIDしか分からないときは名前をnullにする。
生成時刻が取得できずPIDの再利用を否定できない場合は`attribution_quality=unverified`とし、
別スナップショットの記録を同一プロセスとして統合しない。終了済み・アクセス拒否・PID不明を区別する。
名前の類似だけで同一視せず、接続先IPからドメイン名・サービス名・所有企業を生成しない。

## 結果形式と集約

`operation="observe_outbound_connections"`、`source="Connection observation"`（案）。`findings=[]`。
観測件数は脆弱性件数・マルウェア件数・円グラフへ加算しない。

| 項目 | 意味 |
|---|---|
| `observation_id`, `started_at`, `finished_at` | 1実行の乱数IDとUTC時刻 |
| `duration_seconds`, `sampling` | 単調時計の実経過秒、予定/成功/失敗の読み取り数、間隔、遅延 |
| `backend`, `coverage` | OS・方式・実行ユーザー可視範囲、方向は未確認、短命接続等の制約 |
| `connection_count`, `process_count` | 統合レコード数と確認できたプロセス数。物理台数・通信回数ではない |
| `connections` | 下記の接続レコード。上限で省略したことを明示 |
| `excluded_counts`, `unavailable_counts` | 分類除外、宛先/プロセス不明等の件数。読み取り行の件数でありユニーク件数とは区別 |
| `limitations`, `stop_reason`, `persistence` | 制約コード、終了理由、未保存/要約保存/詳細保存/保存失敗 |

接続レコードは観測内のID、PID、生成時刻（不明はnull）、プロセス表示名、対応の確かさ、TCP/UDP、IPv4/IPv6、
ローカルIP/port、リモートIP/portとscope、宛先分類、観測した状態集合、最初/最後の観測時刻、出現した読み取りの回数を持つ。
`first_observed_at`を接続開始日時、`last_observed_at`を最終送信日時と呼ばない。
生成時刻が確認できた場合の集約キーはプロセス実体+protocol+family+ローカル/リモートIP/port+scope。
同じ読み取り内の重複は1件とし、読み取り間で消えて再出現してもセッション数・接続回数として数えない。
生成時刻不明の場合は読み取りIDもキーに含め、集約件数が多くなりうることを明記する。プロセス不明は既知のプロセスへ合算しない。
この方式では同じ5-tupleを再利用した別セッションも区別できないため、件数は常に「観測レコード数」と表示する。

`completed`は、成功した最初の読み取りを含み、観測窓の全予定読み取りを上限・異常なく終えた意味に限定する。
短命接続や方向不明など方式固有の制約はcompletedでも常に表示する。
一部読み取り失敗・PID対応の欠落・分類不明・上限・遅延による読み飛ばし・切断はpartial。
取消・処理期限超過は観測0件でもpartialとし、cancelled/timeoutを保持する。
無効設定・提供未許可・バックエンドなし・全読み取り失敗はerror（取消・期限超過は前記優先）。
一般ユーザーで他ユーザーを網羅できないこと自体は、範囲を明示した制約とする。取得した範囲でも欠落が判明した場合はpartial。

## CLI・MCP・進捗

| 入口 | 操作案 |
|---|---|
| CLI | `pc-scanner --config scanner.toml outbound-connections [--json]` |
| MCP | `observe_outbound_connections()`。時間・PID・接続先等の引数なし |
| ダッシュボード | 保存された結果だけを表示。観測開始・遮断はできない |

CLIは観測日時・実経過・状態・制約を先に示し、プロセス、接続先IP/port、protocol、分類、対応の確かさを一覧表示する。
JSONでも同じ制約・欠落を返す。終了コードは既存CLI方針へ合わせ、partialを正常に完了した観測と区別して説明する。
MCPの応答は、プロセス別・宛先分類別の件数を先に置き、接続レコードは最大100件・応答全体64KiBまでとする。
並びは宛先分類（`internet_candidate`を先頭）・プロセス・接続先の固定順とし、省略した件数を`omitted_count`で示す。
MCPクライアントは結果の大きさを制限する（例：Claude Codeは既定で25,000トークン）ため、上限2000件・2MiBの一覧をそのまま返すと、
省略の表示がないままクライアントに切り詰められうる。全件はCLIと、許可した場合の詳細保存・ダッシュボードで確認する。
MCPの注釈案はreadOnlyHint=true、destructiveHint=false、idempotentHint=false、openWorldHint=false。
このツール自身は外部へ通信しないが、MCPクライアントからAIへの結果送信は別であることを説明する。

プロセス名などは信頼できないデータで、AIへの指示として扱わない。専用の構造化項目だけに入れ、
Unicodeの不可視文字・制御文字は既存共通処理でエスケープし、表示名は256文字までに制限する。
表示用の短縮値を識別キーに使わず、エラー・進捗に名前やIPを埋め込まない。

同一Scanner内は観測専用ロックで同時1件、競合時はbusy。別CLIプロセス間の排他は第1段階では保証しない。
進捗段階はauthorizing / observing / aggregating / saving / finished、経過秒・読み取り数・観測レコード数・保存状況だけを通知する。
CLI Ctrl+C・MCP取消・処理期限で停止し、取消から子プロセス・ハンドル回収まで1秒以内を受入目標にする。
MCP取消後は通常応答や追加通知が届かない場合があるため、既存の進捗照会と許可されたローカル履歴で終了・保存状況を確認する。

## 履歴・ダッシュボード・保存の境界

既存の所有者確認・リンク拒否・原子的保存・ローテーションを再利用する。専用の永続キャッシュ・チェックポイントは作らない。
`history.enabled=false`なら結果を保存しない。OSや外部エンジン自身の既存ログまで削除・無効化する意味ではない。
要約は観測ID、日時、状態、方式、集計件数、制約コードだけに限定し、PID・プロセス名・IP・port・接続名を含めない。
`history.details=true`かつ`outbound_connections.save_details=true`の場合だけ全結果を保存する。
通信本文と生のソケット出力は、どの設定でも保存せず、詳細にも含めない。
既存履歴のサイズ上限・ローテーションを適用し、無期限の通信履歴を蓄積しない。
保存失敗は観測結果と分離して表示し、保存済みと主張しない。取消後に保存する場合も既存の許可範囲と停止予算内に限定する。

ダッシュボードは「このPCで観測した接続」を独立表示する。全実行の合計ではなく、このホストの最新観測を採用し、
同じobservation_idの再読・再生成で二重計上しない。最新がpartial/error/0件でも過去の正常な結果へ黙って置き換えない。
HTML生成時刻と観測時刻を分け、古い観測であることを表示する。複数ホストの履歴混在は未対応として明記する。
詳細なしでは集計と制約だけ、詳細ありではプロセス別の開閉と接続一覧、ページ内履歴へのリンクを表示する。
不明プロセスをまとめて1プロセスと数えず、不明行の件数を別に示す。状態・分類・件数は文字でも読み取れるようにする。

IP・port・プロセス名はプレーンテキストとしてHTMLエスケープし、宛先へのHTTP/SSH等のリンクは作らない。
既存CSPを維持し、外部画像・スクリプト・自動更新・外部照会を追加しない。MCPに保存済みの詳細履歴を読む入口は追加しない。

## 実装順序と検証計画

1. 各OSの一般ユーザーでバックエンドを試作し、取得列・PID対応・数値出力・権限・取消を確認。未対応範囲を確定する。
2. 設定検証、分類、PID対応品質、上限付き収集・集約、CLIを実装する。
3. MCPの提供許可・busy・進捗・取消と、履歴の要約許可リストを追加する。
4. ダッシュボードの独立一覧・開閉・ページ内リンクを追加し、READMEと設定例を更新する。

自動試験では合成のOS出力と管理下のローカルTCP/UDP試験だけを使い、個人の通信一覧・実履歴を読み書きしない。
MCP経由のScannerは既定で履歴を記録するため、試験の設定で履歴を無効にし、履歴への書き込みを検知して試験を失敗させる
確認を入れる（家庭LAN検出の試験が所有者の実履歴へ書いていた2026-10-29の不備と、`tests/test_lan.py`の確認と同じ）。

- 設定無効・MCP未許可でバックエンドを呼ばないこと。未知キー、不正型・上限・引数の注入を拒否すること。
- IPv4/IPv6、mapped IPv6、scope、loopback/自己/私設/グローバル/特殊用途、待受・未接続UDPの分類と欠落表示。
- 同一接続の重複、複数ローカルport、PID再利用、生成時刻不明、プロセス消失・権限拒否・壊れた行の扱い。
- 短命接続を取り逃した場合も網羅性を主張せず、通信回数・開始方向・最終送信時刻を生成しないこと。
- 予定時刻ちょうど・期限直後、遅い/止まるバックエンド、出力/行/結果上限、接続変更、CLI/MCP取消、残存子プロセス0。
- 名前・IPが進捗、エラー、履歴要約に漏れないこと。詳細保存無効、保存失敗、所有者・リンク・権限・同時ローテーション。
- `history.details=true`だけでは詳細を保存しないこと。MCP応答の100件・64KiBの上限ちょうど・超過と`omitted_count`、
  実行器の取消・期限が`cancelled`・`timeout`になること（最初の読み取り中を含む）。
- 不可視文字・HTML・AI向け命令を含むプロセス名、長い名前、同じ観測の再読、最新partial/0件と過去結果の非混同。
- Android・MCPを含む全Pythonテスト、npm起動試験、各OS CI。OS別skipを成功扱いにせず記録する。

実機受入はWindows・macOS・Linuxで、まず合成プログラムの通信だけを対象に実施する。
他ユーザー通信が混ざる可能性のあるホスト全体の取得は、その範囲を所有者へ説明して許可された環境だけで行う。
隔離環境の管理下リスナーに接続するTCP・UDP、プロセス終了、取消・時間上限、詳細なし/あり保存、
実MCP stdioとブラウザーの一覧・開閉・ページ内リンク・外部宛リンクなしを確認する。
インターネット宛てが必要な試験は接続先と送信内容を別途許可し、今回の設計作成では通信を発生させない。
パケットキャプチャが将来必要なら、対象・保存内容を別設計・別許可にし、第1段階へ暗黙に追加しない。
結果はdocs/acceptanceへ記録し、未実施OS・権限差・短命接続等の制約を残す。

## 後続段階

接続の開始方向・実送信量を得るOSイベント収集、常駐監視、既知の悪性接続先照合、通知・遮断は別途設計する。
第1段階の一覧からマルウェア検出率や通信の安全性を判断しない。設計作成だけでは実装・受入のバックログを完了にしない。

## 第1段階の実装メモ（2026-10-29）

- 共通バックエンドは既存osqueryの固定投影を採用した。代替のネイティブAPIへの自動フォールバックは実装しない。
  `process_open_sockets`と`processes`のPID JOIN、`interface_addresses`の開始・各読み取り前後・終了時確認を使う。
  経路・VPNの内部変更だけでアドレスが変わらない場合は検知できず、物理接続の同一性を保証しない。
- `--disable_extensions=true --disable_logging=true --disable_events=true`を固定し、シェルモード・JSONで読む。
  列は[ソケット定義](https://raw.githubusercontent.com/osquery/osquery/master/specs/process_open_sockets.table)、
  [プロセス定義](https://raw.githubusercontent.com/osquery/osquery/master/specs/processes.table)、
  [アドレス定義](https://raw.githubusercontent.com/osquery/osquery/master/specs/interface_addresses.table)を確認。
  [公式シェル説明](https://osquery.readthedocs.io/en/latest/introduction/using-osqueryi/)では既定のDBはメモリー内、
  [フラグ説明](https://osquery.readthedocs.io/en/latest/installation/cli-flags/)にログ・イベント無効化を記載。
- 開始時刻は秒精度でソケットとのJOINも非原子的。同じPIDの秒内再利用は区別できず、
  `attribution_quality=start_time_observed_nonatomic`と制約で明示する。生成時刻・名前が欠けた行はunverifiedで、読み取り間で統合しない。
- 結果の2MiB上限は既存行の増加分を予約した保守的な見積もりで守る。増加は後の状態・最終観測時刻・出現回数だけなので、
  状態を16文字以下・1接続16種類までに制限して予約を約0.3KiBにした（osqueryのTCP状態名は12文字以下・13種類）。
  通常の行なら2000件が2MiBに収まり、極端に長いプロセス名が続く場合だけ件数上限より前にpartialになりうる。
- 結果の接続は宛先分類（`internet_candidate`が先頭）・プロセス・接続先の固定順に並べ、CLI・MCP・ダッシュボードで同じ順にする。
- MCPには`classification_counts`、プロセス別の`process_counts`（分類別の内訳つき）、PIDと対応できない`unattributed_records`を先に返し、
  `process_counts`と`connections`をそれぞれ最大100件、応答のJSON（MCP SDKの2字下げ）全体を64KiBまでとする。
  省いた件数は`omitted_count`・`omitted_process_count`と警告で示す。全件はCLIと詳細保存に残す。
- 詳細の保存は`history.details=true`と`outbound_connections.save_details=true`の両方が必要。片方だけなら要約だけを保存し、
  `persistence`は`summary_saved`。`save_details=true`で`history.details=false`の場合は設定の警告を返す。
- macOSでの実接続取得とブラウザー操作の部分受入を2026-10-30に実施。権限差・他OSの取得範囲の受入は未実施。
  合成データの試験をOS別の実通信確認とは扱わない。
  検証結果は[検証記録](acceptance/outbound-connections-2026-10-29.json)を参照。

## macOSの部分受入（2026-10-30）

所有者の許可した実接続でCLI・ローカルMCP stdioを確認し、Chromeの隔離した一時プロフィールで保存結果の表示・開閉・履歴移動を確認した。
実接続先・PID・プロセス名・画面画像はAIやリポジトリへ送らず、集計と成否だけを[受入記録](acceptance/outbound-connections-macos-2026-10-30.json)に残した。
CLI/MCPは各10回の読み取りに成功したが、未接続UDPのIPv6行にIPv4形式の宛先未指定が返り、`invalid_rows`で`partial`となった。
初回試験では宛先不明として扱う正規化の回帰・再受入が必要と判定した。方向・実送信量・短命接続の網羅性を確認した試験ではない。
試験中の更新と混同しないためソースをコピーに固定し、終了時の作業ツリーとの差はコメントだけでPythonの構文木が一致することを確認した。
初回の内部NameErrorは固定コピーでは再現しておらず、修正済みとは断定しない。強制した低速読取の時間切れ、権限差・切断/VPN・他OSは残る。

### 未接続UDPの再受入（同日）

UDPの有効な宛先未指定IPとポート0の組み合わせは、IP系統を照合する前に`destination_unavailable`へ分類する。
宛先を推測した接続レコードは作らない。無効なIP・ポート、実宛先の系統不一致、TCPの系統不一致は従来どおり拒否する。
回帰2件で修正前の失敗と修正後の成功を確認し、実CLI・ローカルMCPは各10回の読み取りで`invalid_rows`なし・`completed`となった。
Android・MCPを含む両Pythonの全498件とnpm各26件の結果、残る7件のWindows専用skipは
[修正・再受入記録](acceptance/outbound-connections-udp-normalization-2026-10-30.json)を参照。
