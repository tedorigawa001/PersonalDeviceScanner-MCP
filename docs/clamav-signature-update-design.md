## 方針と方式比較

### 第1段階の具体化

- `[clamav_updates]` は既定無効。macOS/Linuxの非root POSIXユーザーのみ有効。
  `directory`・`freshclam_binary`・`sigtool_binary` を所有者が固定し、`update-clamav-signatures` CLIだけから更新する。
  `local.clamav_database_directory` との併用は拒否し、チェック・通常／分割／選択再検査を私有世代へ固定する。
- `ScriptedUpdates no` に決定し、main/daily/bytecodeの完全版CVDのみ公開する。
  freshclam正常終了に加え、sigtoolの署名行・検証成功、必須ファイル・版後退拒否、clamscan読込みを確認する。
  ファイル内容ハッシュをcheckpoint文脈に使い、旧メタデータ方式の証跡とは区別する。
- 更新・公開は別のプロセス間排他ロック。検査は共有の世代leaseを取得し、公開を跨いでも保存先を変更しない。
  公開ロックは参照の読取り・lease取得と参照の切替だけに使い、内容ハッシュとfsyncはロック外で行う。
  同時に始まった検査・確認は短く待って続行し、即失敗させない。定義保存先の確認は、プロセス検査・脅威リストの
  私有保存先とは別のスレッド内排他を使い、脅威リストのダウンロード中もそれらの処理を待たない。
  選択削除は更新ロックと対象世代の排他leaseで保護し、現行・使用中・最後の過去世代は削除しない。
- 保存先の上位フォルダーは、モードビットに加えmacOSのACLでも、他ユーザーに項目の追加・削除・名前変更を許すものを拒否する。
  他ユーザーが保存先を退かせると、次の更新が待機情報のない新しい保存先で始まり、待機を守れないため。
  一覧の使用中確認は過去世代だけに排他leaseを試し、検査が共有leaseを取る現行世代には試さない。
  管理処理は大きな定義の検証・削除中に公開ロックを保持せず、現行世代で始まる検査を妨げない。
  通常検査の外部定義変更もpartialとし、完了証跡を保存しない。
  変更検出は独自定義を含む全項目の同一性で行い、変更のない独自定義があるだけではpartialにしない。
- 過剰な再試行とfreshclam固有待機の破棄を避けるため、第1段階は開始前に24時間の待機とpendingを永続化する。
  失敗・中断・クラッシュではpendingを残し、自動再試行を停止する。成功時、または期限後の所有者CLI復旧だけでpendingを解除する。
  失敗作業領域（freshclam管理ファイルを含む）は私有のまま保全する。
  freshclamの終了0だけでは成功と判定しない。標準出力・標準エラーの既知の429／cool-down通知を検出したら、
  配布元状態の同期保存を確認後、`partial`／`rate_limited`・`recovery_required=true` とし、pending・stageを保持する。
  公開・成功時の削除には進まず、保存障害があれば通常の失敗として新しいstageと未完了の同期記録を残す。
  バイナリ状態やログのローカル日時は独自解析せず、保存済み最短期限より長い配布元待機を所有者が確認してから復旧する。
  freshclamは通常の更新行にもCVDヘッダーの作成者名（`builder`）を出すため、そこに429の通知文があっても `rate_limited` になる
  （2026-11-10の脆弱性チェックで偽のfreshclamにより再現）。公開せずpendingを保持する安全側の誤判定で、本物の429を見逃さないことを優先して
  検出範囲は狭めない。配布元が作成者名を変えられるかは未確認。
- 現行・旧世代・失敗stageを最大4件とし、取得前に4GiB以上の空きを要求する。上限前に所有者CLIで選択整理する。
  これは取得中のディスク使用量のハード上限ではない。出力定義の総量は2GiBまで確認する。
  自動削除・容量クォータは未実装。容量不足やpending時は所有者が一覧・原因を確認し、下記CLIで復旧・選択削除する。
  定義ファイルがそろっていないフォルダーは一覧で `incomplete` と示す。上限には数え、削除できる。
  最後の過去世代として扱うのは、現行世代と同じ確認（本人専用の3つの定義だけで、先頭部分とサイズが正しい）に通るフォルダーだけとする。
  リンク・未知のファイル・壊れた定義を含むフォルダーが並んでも、使える最後の過去世代の保護は外れない。
  CLIで管理できない `stage-*` の名前も上限に数え、一覧は件数を `unrecognized_entries` と警告で示す。所有者が手で確認する。
- MCP更新、Windowsバックエンド、OSサービスの導入確認は未完了。

### 所有者向け復旧・世代整理CLI（2026-11-01）

- `clamav-signature-store list` は世代・失敗stageのID、メタデータから求めた確認用revision、現行／使用中／保護理由を返す。
  実パスや内部ファイル名を出さず、復旧用の全体revisionと保存済み待機の最短UTC時刻も返す。
- `recover --revision ... --not-before ...` は、所有者が原因と配布元の全待機指示を確認した明示操作。
  タイムゾーン必須の期限を受け取り、既存期限より短い指定と期限前の復旧を拒否する。
  延長は即永続化し、後の呼出しで短縮できない。期限ちょうどで解除し、1マイクロ秒前は解除しない。
  現行世代があれば内容ハッシュを再確認し、孤立世代の自動昇格・ダウンロード・時刻変更は行わない。
- freshclam終了後は失敗も含めて `freshclam.dat` を私有の `provider.dat` へ同期保存し、次回freshclamへ戻す。
  `provider-sync.json` に起動前のpendingと対象stageを同期保存し、正本の永続保存とstageとのハッシュ一致後にsyncedを記録する。
  保存失敗／クラッシュでpendingなら対象stageから保存をやり直し、確認できなければ停止状態を維持する。
  syncedの場合も正本のハッシュ一致を再確認する。証跡があれば古いstageが複数あっても今回の保存元を特定できる。
  証跡のない旧形式では古い正本の存在を根拠にせず、一意なstageから同期し直す。複数候補・保存元欠落・曖昧な旧正本は拒否する。
  保存元も正本も存在しない試行は「待機情報なし」と明示的に記録し、旧正本だけが残る場合と区別する。
  バイナリの待機形式を独自に解析せず、freshclamに引き継ぐ。所有者の期限指定は配布元の待機を短くする権限ではない。
  拒否が続く間も検査は現行世代で続くが、定義は古くなる。解消できない場合の出口は `enabled=false` でOS管理の定義へ戻すか、
  配布元の全待機の経過を確認してから新しい私有保存先を設定すること。待機情報の削除・書換えや強制解除は出口にしない。
- `delete ID --revision ...` は1つの管理ディレクトリのみを対象とする。待機情報・現行参照は削除しない。
  削除した世代のleaseファイルは排他leaseを保持したまま消す。IDは再利用されず、検査がleaseを取るのは現行世代だけのため、
  削除後に同じleaseを取る処理はなく、管理項目数の上限に向けて蓄積させない。
  未復旧stage、現行／使用中／最後の過去世代、古いrevision、不明ファイル・ACL・権限・所有者・リンク・未取得を拒否する。
  上限128メタデータ・深さ3・事前確認30秒を適用し、記述子を使ってリンクを辿らず削除する。
  I/O障害や操作中断で削除が一部済む可能性はあり、一覧を再取得して残りを確認する。現行世代には書き込まない。
- 更新と管理は同じプロセス間更新ロックで排他する。管理はCLI限定で、MCPツール・Scanner.invokeには登録しない。
  管理者パスワード・強制削除・任意パス指定は提供しない。Windowsの管理も更新基盤の実装・受入までは無効。
- [実装検証記録](acceptance/clamav-signature-maintenance-2026-11-01.json)。合成保存先の回帰試験であり、
  前回の実更新保存先の待機解除・削除や、実freshclamによる障害復旧の受入は行っていない。
- [Mac CLI実機受入・追加レビュー](acceptance/clamav-signature-maintenance-macos-2026-11-01.json)では実検査中の現行／使用中保護・選択削除、
  実時計での試験用待機期限の維持・復旧・stage整理を確認した。実通信障害の発生や既存の実待機解除とは区別する。
  追加で見つかった「正本保存失敗後に旧情報のまま復旧する」問題は、上記の試行ごとの保存証跡・再保存と
  [修正検証記録](acceptance/clamav-provider-sync-fix-2026-11-01.json)で対応した。実配布元の待機違反を起こす試験は行わない。
  [修正後のMac保存障害受入](acceptance/clamav-provider-sync-native-macos-2026-11-01.json)では試験正本のmacOS書換え禁止属性で
  実際の置換失敗を発生させ、期限後も復旧しないことと、属性解除後に新しい内容を再保存して復旧することを確認した。
  試験用pending／短い期限と実freshclam通信障害は区別する。既存の実待機・OS定義を変更せず、禁止属性は解除済み。
  [Linux Docker受入](acceptance/clamav-signature-update-linux-2026-11-01.json)ではUbuntu 24.04 aarch64／ClamAV 1.5.4で
  実取得・署名・公開・私有権限、実検査中の世代保護と選択削除、書込み上限による実保存失敗と再保存後の復旧を確認した。
  実取得後は通信を切り、実更新の24時間待機と復旧用の代役保存先を分けた。実通信障害や別版更新、他Linux環境・Windowsは未確認。

対象は公式のmain・daily・bytecode定義。エンジン本体、起動スクリプト、独自定義の更新は対象外。
検査要求による暗黙の更新は行わない。個人ファイル・検査結果を更新サービスに送らない。

| 項目 | OS側freshclam自動更新 | MCPからの明示更新（将来実装） |
| --- | --- | --- |
| 推奨用途 | 現在のMacとOS管理の共有定義 | 所有者が選択した専用の一般ユーザー環境 |
| 更新権限 | OSのサービスアカウント | スキャナー実行ユーザーのみ |
| 導入・設定 | 所有者がOSの管理手順で実施 | 所有者がローカル設定で明示的に有効化 |
| MCPの役割 | 状態・鮮度・更新案内の読み取り | 固定のfreshclamによる更新要求・進捗・結果 |
| 検査との関係 | 外部更新の検出が必要 | 世代固定と公開処理の排他制御が可能 |
| 正常データの保全 | OS管理の更新処理に依存。アプリから復旧書込みしない | 別領域で検証後に世代を公開。旧世代を保持 |
| 定義の改ざん耐性 | サービスアカウント所有なら、スキャナー実行ユーザーのプロセスから書き換えられない | 他ユーザーからは保護されるが、同じユーザーで動く他プロセスは書き換えられる |
| 注意点 | アプリのロックでサービスを停止できない | 定義の二重保有・空き容量・保守が必要 |

このMacの通常保存先は `_clamav` 所有で一般ユーザーのプロセスから書き換えられないため、まずOS側自動更新＋読み取り専用確認を推奨する。
自動更新が実際に設定済みかは別途確認が必要。手動更新成功を自動運用の完了と扱わない。
MCPがOSサービスを起動・停止したり、通常保存先を直接更新する方式は採用しない。
両方式が同じ保存先に書き込む構成も禁止する。

## 権限・設定・公開範囲

- sudo、管理者パスワード、認証ダイアログの操作、昇格ヘルパーをMCPに持ち込まない。
  権限不足は管理者によるOS設定が必要と案内し、所有者・ACL・アクセス権を自動変更しない。
- 明示更新は既定無効。所有者が固定した実行ファイル、公式配布設定、専用ローカル保存ルート、
  時間上限、容量上限、CA設定だけを使う。ツール引数からコマンド、引数列、URL、パスを受け取らない。
  freshclam設定は許可した項目から生成し、任意の既存設定をそのまま取り込まない。
  コマンド実行フック、NotifyClamd、独自ミラー・独自定義・デーモン化は初期実装で許可しない。
- TLS証明書検証と公式定義の検証を無効化しない。環境変数の全面継承は禁止する。
  プロキシ認証など秘密値が必要な構成は初期実装対象外とし、設定・標準出力をMCPへ転送しない。
- 専用保存ルートは本人所有・ディレクトリ0700／ファイル0600相当。既存の所有者・リンク・
  ハードリンク・ACL検証を適用し、macOSの許可ACL、Windowsの他者アクセスを拒否する。
  WindowsはネイティブACLによる実装・実機検証が完了するまで更新を有効にしない。
  クラウド同期・未取得項目、ネットワーク保存先、リンク／reparse経由を使用しない。
  これは他ユーザーからの保護であり、同じユーザーで動くプロセスによる改ざんは防げない。
- 将来の `update_clamav_signatures` は `readOnlyHint=false`、`openWorldHint=true`。
  ローカルの有効化はクライアント側の実行許可の代わりにならない。README・SECURITYの説明も更新する。
  Android端末はadbで接続する検査対象であり、定義更新の対象外とする。

## OS側の運用手順

所有者がOS・導入元に合ったfreshclamサービスを設定し、実行ユーザー、参照先、起動時と定期実行、
最終成功・失敗のログを確認する。アプリは設定を変更せず、検査と状態確認が同じ定義を参照するか確認する。
鮮度が古い／不明ならpartial・警告とOS側更新の案内を維持する。更新を待って無期限に検査を止めない。
実際のサービスの設定・失敗通知・再起動後の継続はOS別の受入項目とする。

公式freshclamは公式定義を取得し、既存定義への差分適用も行う。
直接ダウンロードスクリプトへ置き換えない。
根拠：[公式の定義管理](https://docs.clamav.net/manual/Usage/SignatureManagement.html)。
頻繁な再試行は避け、429やfreshclamの待機指示を尊重する。
根拠：[公式FreshClam FAQ](https://docs.clamav.net/faq/faq-freshclam.html)。

## 明示更新の処理と失敗時の保全

以下はアプリ側で実現する設計であり、freshclam自体の複数ファイル一括更新保証ではない。

1. 保存先・権限・容量・固定実行ファイルを検証し、保存ルート単位のプロセス間更新ロックを取得する。
   同時要求はbusyを返す。再試行制限を確認し、許可された開始試行を保存してから通信する。
   最低1時間の間隔を既定とし、freshclamが指定するより長い待機を優先する。再起動・キャンセルで解除しない。
2. 現在の正常世代を別の作業領域へコピーし、freshclamを一回実行する。初回は空から取得する。
   共有ハードリンクは使わない。freshclamの管理ファイルも私有領域で保管し、待機状態を失わない。
3. freshclamの正常終了（取得時の検証を含む）に加え、必須定義、対応エンジンによる全定義の読込み、版・日時・内容ハッシュを確認する。
   不足・混在・不明な追加ファイル・版の後退・検証不能は公開しない。鮮度不足なら警告を付ける。
   最新かどうかのオンライン確認と、定義作成日時による鮮度は別の項目とする。
   差分適用で組み立てた `.cld` は電子署名を持たず、公開元の署名を後から再検証できない。
   このMacの `daily.cld` も `sigtool --info` に署名行がなく、外部の `.sign` もなかった。
   `sigtool` の「Verification OK.」を署名の確認として扱わない。公開時に記録する内容ハッシュは誤操作・破損の検出用で、
   同じユーザーのプロセスによる改ざんは防げない（世代の変更禁止も同様）。署名付きの完全版 `.cvd` だけを使う構成
   （freshclamの `ScriptedUpdates no`。通信量は増える）は検討候補とする。
4. 検証済みデータを変更禁止の世代ディレクトリとして確定し、公開ロック下で現行世代の小さな参照ファイルを
   安全に置換する。必要な書込み同期とクラッシュ復旧を実装する。世代内部には管理用参照ファイルを置かない。
   参照は安全に検証した実ディレクトリへ解決し、既存のリンク拒否を緩和しない。
5. 公開した世代を再確認し、updated／unchangedを返す。内容が同じなら現行世代を維持する。

通信・検証・容量不足・時間切れ・公開前キャンセルでは現行参照を変更しない。
作業領域は失敗と識別し、次回の検査から参照させない。破損した現行定義しかない場合は「旧正常定義を保持」と偽らず使用不能を返す。
公開後のキャンセルは巻き戻さず、公開済み・応答中断を記録し、再照会できるようにする。
公開結果を確認できない障害はunknownとし、成功を推測しない。OS管理の定義にはこの復旧処理で書き込まない。

子プロセスは時間上限・キャンセルで回収し、その後にロックを解放する。ログは有界化・匿名化する。
クラッシュ後はロック回収、参照先と世代の整合性確認、未公開作業領域の安全な整理を行う。
旧正常世代は最低1世代保持し、使用中の世代は削除しない。容量不足で安全な保持ができなければ更新を断る。
保持数・作業領域の期限と削除方法は所有者向けCLIに限定し、MCPへ任意削除を公開しない。

## 検査との競合と世代固定

専用保存先では、検査開始時に現行世代を固定し、定義確認と全clamscanへ同じ明示的な保存先を渡す。
長い分割検査の途中で新しい世代へ切り替えない。更新は別世代で進められ、公開しても既存の検査は旧世代を使い続ける。
古い世代で完了したことと、新世代による再検査が必要なことを結果に示す。
世代の使用中保護はプロセス間の共有ロック、削除は排他ロックで実現し、PIDファイルだけで判定しない。
更新ロック→短時間の公開ロック→世代保護の順序を固定し、検査は公開ロック内で世代保護を取得してから公開ロックを解放する。
削除は使用中世代を待たずに飛ばす。検査から更新ロックを取得しない。既存のサーバー内engine_lockだけに依存しない。

OSサービスや手動freshclamはこのロックへ参加しない。そのためOS管理先では検査ジョブの前後に定義一式の
識別情報・メタデータ・版を確認し、変更・不明なら当該結果をpartial／定義変更として扱い、完了証跡を再利用しない。
検出済み所見は保留の文脈付きで残す。既存のまとめ検査の前後確認を通常・分割経路にも整合させる。
前後確認は更新と復元が間に入る競合まで完全に排除する保証ではない。
厳密な同一定義保証が必要な運用では専用の世代固定方式を選ぶ。サービス停止や定義コピーを無断で行わない。

## 再開結果の失効と集計

- 再利用のキーは定義一式の内容識別子、エンジン実体・版、検査の意味に影響する設定、対象の検証情報。
  現行実装の定義manifestはメタデータも含むため、同一内容の再配置でも失効し得る。
  内容識別子への移行と旧schemaの安全な扱いは実装時の必須変更とする。
- 内容が変われば旧区画の完了・除外を再評価する。履歴・過去の所見を削除せず「旧定義の結果」と明示する。
  内容不明、エンジン変更、意味のある設定変更も失効。同一バイト列の更新確認だけなら失効させない。
  mtimeのみでは内容の同一性を保証しない。検証した変更禁止世代のハッシュを使う。
- 更新成功を理由に実行中検査の台帳を外部から書き換えない。次の再開時に比較し、旧完了を再利用せず再検査する。
  選択再検査の古いrevisionは拒否し、まず通常の再開で台帳を更新するよう案内する。
- ジョブの全メンバーを同じcheckpoint版で確定し、中断グループを部分的な完了として加算しない。
  再開ごとの累積件数や過去履歴を合算しない。クラウド未取得項目は再開でも属性だけで除外し、取得しない。
- 更新失敗で正常世代が変わらない場合、失敗自体を再利用失効の理由にしない。
  ただし鮮度の期限超過や対象変更は別に評価する。

## CLI・MCPの結果と案内

読み取り専用確認には参照方式、エンジン版、定義版・作成日時・鮮度、更新可否・案内を示す。
更新結果はupdated／unchanged／busy／rate_limited／failed／timeout／cancelled／unknownを区別し、
段階、経過時間、公開有無、旧正常世代の保持状況、再開結果の再評価要否、次回試行可能時刻を返す。
進捗は準備・取得・検証・公開・終了の段階とし、取得率・残り時間を推測しない。
実パス・ユーザー名・認証情報・接続先の実IP・生ログはMCPと通常履歴へ載せない。
更新確認時刻、更新成功時刻、定義作成日時を分け、不明値を成功日時で埋めない。

鮮度は既存の `max_signature_age_days` と整合させ、期限ちょうどを許容し、1マイクロ秒超過をstaleとする。
未来日時・解析不能はfreshにしない。更新成功・freshはマルウェア不在の保証ではない。
更新後も検査時点で鮮度を再判定し、鮮度不足は既存のpartial・警告に反映する。

## 実装順序と受入条件

1. OS側の読取確認と設定案内を整備。専用保存先の世代・権限・ロック・復旧基盤を実装する。
2. 所有者限定CLIで更新・変更なし・失敗保全を確認後、既定無効のMCP更新を追加する。
3. 全検査経路の世代固定とチェックポイント移行、README・SECURITY・設定例を整合させる。

回帰テストは次を必須にする。

- 更新／同一内容／版後退／破損／必須定義欠落／読込み失敗／空き容量不足。
- TLS・通信失敗、429と待機指示、プロセス再起動後の制限保持、秘密値の非露出。
- 更新同士・複数プロセスの検査との競合、長い検査中の公開、旧世代使用中の削除拒否。
- 公開前後のキャンセル・時間切れ・クラッシュと子プロセス回収、ロック解放、保存状態の真実性。
- 外部freshclamによる検査中変更・メタデータ取得不能、再利用拒否と所見保持。
- 同一内容のmtime変更、実内容変更、エンジン／設定変更、旧checkpoint、古い選択revision、二重計上防止。
- 不正所有者・ACL・リンク・reparse・クラウド未取得の拒否と、対象の非取得。
- 鮮度の期限ちょうど・1マイクロ秒超過・未来・不明、CLI／匿名MCP／履歴の整合。

Android・MCPを含む全テストを実行し、Macの実freshclam・ClamAVで専用合成データを使って受入する。
Linuxは個人フォルダーをマウントしないDockerで、WindowsはCIと実Windows環境の受入を区別する。
外部サービス側の失敗はローカルの制御した代役でも再現し、実サービスを過剰に呼び出して障害を起こさない。
第1段階の検証結果は[実装検証記録](acceptance/clamav-signature-update-phase1-2026-11-01.json)に記載する。
自動更新設定は変更していない。Macは異なる公式定義版への実更新と再開失効まで確認済み。
Linux Docker aarch64も異なる版への更新・再開失効まで確認済み。
ローカルの制御した配布元でのHTTP／HTTPS転送障害からは、期限後の復旧と再試行の成功まで確認済み。
ローカルの制御した配布元での429／Retry-Afterは、48時間の配布元待機の保持と、修正後の `partial`／`rate_limited` 判定まで確認済み。
ローカルでのTLS接続中断・未信頼CA・証明書名の不一致は、`error`／`failed` としてpendingを保持し、期限後の復旧と再試行の成功まで確認済み。
429の待機が自然に明けた後の所有者の復旧と再試行の成功は、8保存先中6件で確認済み（残る2件は試験の不備で失敗し、待機を保持）。
残る2件のうちhttp-seconds-cachedは、2026-11-12の追試で期限後の復旧と再試行に成功した。
他のLinux環境・Windowsの受入、凍結した429の1件に代わる別IDでの再受入、実配布元での障害と待機は残る。
