# ClamAV定義の手作業が残る復旧経路

2026-11-21、0.11.4の所有者向けローカルCLIを対象に作成。通常の待機後復旧と優先1の削除後の後片付けは実装済み。優先2の初回公開前の容量復旧は設計案。
[定義更新の設計](clamav-signature-update-design.md)／[過去世代の保護設計](clamav-previous-generation-protection-design.md)

## 現行CLIでの切り分け

稼働中の専用保存先では、まず `pc-scanner --config scanner.toml clamav-signature-store list` で一覧を取り、直前のCLI出力と更新ログを保存する。一覧は更新ロックを取得し、ロックファイルがなければ作成し得る。凍結原本など、書き込みを伴わない調査が必要な保存先は、既存の保全手順に従って調べる。

| 状態 | 現行の対応 |
| --- | --- |
| `pending_recovery`。現行の定義と配布元状態を確認できる | 保存済みの最短期限と配布元の指示のうち遅い方が過ぎてから、最新一覧の `recovery_revision` とタイムゾーン付きの日時で `recover` を実行する。保護されたstageから配布元状態を再保存できる場合はCLIが行う。復旧後に一覧を取り直すと、安全性を確認できた不要stageを選択削除できる。 |
| `partial` に `deleted` と `lease_removed: false` がある | 世代ディレクトリの削除は実行時に確認済み。一覧の `data.cleanup` から対象を選んで `cleanup` で再試行する。残ったリースが使用中なら保留する。0.11.4以前の削除は削除の記録を残さないため、保護中の過去世代より新しい位置にあった世代は次の公開のあとに候補に出る。それまで世代削除は `previous_unavailable` で保留される。 |
| `deleted` と `directory_synced: false` または `history_updated: false` がある | 一覧の `data.cleanup` から再試行する。同期未確認の場合は再起動後の永続性も未確認。履歴の置換は済んでいても、同期や読み戻しが確認できるまで成功としない。0.11.4以前の削除で保護中の過去世代より新しい位置にあった世代は、上と同じく次の公開のあとに候補に出る。 |
| `missing_history` で世代が4枠を占める | 現行参照 `current.json` が存在せず、世代の削除も次の更新も拒否される。初回公開の失敗で残った候補と、以前に公開されて参照を失った世代は、参照の欠落だけでは区別できない。現行参照がない保存先でも、通常のstageには別の削除条件が適用される。 |
| `history_unavailable`、`previous_unavailable`、`no_valid_previous` | 参照または保護候補の状態が確認できるまで保全する。一時的な入出力障害や権限不備を解消してから一覧を取り直す。候補の版番号や署名確認記録だけから公開済みと判断しない。 |
| `unrecognized_entries`、stageの `unavailable`、配布元同期の根拠不足 | 認識できない `stage-*` も容量に数える。未知ファイルや欠落・不一致・複数候補のある配布元状態は、保存先とログを一組で保全して調査する。更新を続ける必要があれば、既存の運用にあるOS管理定義への切替、または配布元の全待機が経過した後の新規専用保存先を検討する。 |

合成保存先に参照のない世代を4件置き、待機が経過した状態で確認した。全4件が `missing_history` となり、1件を選択しても削除は拒否された。更新は容量不足で終了し、エンジン起動は0回、一覧と `attempt.json` の内容は変わらなかった。既存の定義関連テスト113件も成功した。

## 優先1 削除済み世代の後片付け

世代を削除した後のリース除去・ディレクトリ同期・公開履歴更新を、所有者CLIから再実行できるようにした。一覧の `data.cleanup` にはID、再確認する処理、リビジョンが表示される。

- 削除開始前に対象IDと削除前後の公開参照のハッシュを `<ID>.cleanup.json` に耐久保存する。削除後に世代と検証記録がともに無いことを確認し、削除時の記録または正常な過去世代を確認した上での古い公開履歴を根拠に候補を表示する。公開参照が後の公開で変わった場合は、最新の参照で正常な過去世代を確認し直す。
- 所有者がIDと最新リビジョンで1件を選ぶ。更新ロック下で世代と検証記録の不在、現行IDとの不一致、過去世代の保護を再確認する。リースが残る場合は本人所有の単一リンクであることを確かめ、排他取得できるものだけ除去する。参照や対象が変わった場合、ロックが使用中の場合、権限や状態を確認できない場合は保留する。
- 親ディレクトリ同期を確認してから、必要な場合だけ公開ロック下で対象の履歴を更新し、読み戻す。公開ロックは参照更新の間だけ取り、定義の照合中も現行世代で検査を開始できるようにする。残りがあれば `partial` と個別の確認結果を返す。処理を確認できたら後片付け記録を整理する。

## 優先2 初回公開前の容量不足

### 対象と既存保存先の扱い

対象は、専用保存先の**初回公開候補のうち、参照の置換を開始する前に止まったことを耐久記録で確認できるもの**。最初の正常公開後は優先1と過去世代の保護規則を使う。

現行実装は `stage-*/candidate` から候補を世代ディレクトリへ移し、署名確認記録を移してから `current.json` を置換する。参照の不在だけでは、移動後・置換前の停止と、公開後に参照を失った状態が同じに見える。署名、版番号、ファイル日時、稼働ログにも公開境界を証明する役割は持たせない。

- 記録を作る新形式は、所有者が新しい専用パスを指定して利用する。設定キー `[clamav_updates].store_format = "tracked-first-v1"` を追加する案とし、旧版は未知のキーとして構成を拒否する。CLI・MCPは保存先を共有する前に対応版へそろえる。旧設定を作り直して同じパスへ接続する運用や、記録だけを古いバックアップから戻す運用はサポートしない。
- 新形式の初期記録は、今回の初期化で排他的に新設したディレクトリにだけ作成し、親を同期してから利用する。初期化完了前に止まった保存先や、記録がない既存保存先を後から「初回」と認定しない。既存保存先の形式・定義・待機状態の自動移行は行わない。
- 現行参照が無く、根拠不明の世代が存在する場合は、同じ保存先で通常更新を保留する。判定は容量の確認と同じく、新しい待機記録の書き込み・freshclam起動より前に行い、配布元への接続、新しい待機、stageの作成を起こさない。空の履歴を作って既存世代を削除可能な孤立世代へ読み替える経路を塞ぐ。これは旧形式にも適用する。正常な現行参照がある既存保存先の通常運用は従来の保護規則に従う。
- 旧形式への適用は、0.11.4で導入した「参照が一度もなかった保存先では、初回の切替の失敗で残った世代を記録せず、最初の公開のあとで削除できる」動きを取り消す。実装時は、READMEの同じ説明（英語版・日本語版）とテスト `test_folders_left_by_failed_first_switches_stay_deletable_after_the_first_publication` を改め、既存の設定に影響しうる変更としてリリースノートの冒頭に書く。参照が無く来歴不明の世代が1件でも残る既存保存先は、空き枠があっても更新も世代の削除もできない。その保存先は保全し、配布元が指示したものを含む既存の待機期限をすべて確認して自然に経過した後、新しい専用パスの新形式へ移る（`a1e6266` のレビューで追記）。

### 初回公開を記録する順序

保存先直下の私有JSON `first-publication.json` を使う。形式番号、保存先のランダムID、公開段階、切替対象ID、容量に収まる数の候補記録を保持する。候補記録は世代ID、元stage ID、3つのCVDの版と全体ハッシュ、署名確認記録のハッシュを結び付ける。形式・件数・読み取りサイズ・IDを検査し、本人所有、単一リンク、安全な権限とACLのファイルだけを読む。置換のたびにファイルと親ディレクトリを同期し、期待値を読み戻す。既存の更新ロックを使い、古いライターやロック外の同一ユーザーによる並行書き換えを前提にしない。

| 段階 | 記録と操作 | 中断後の扱い |
| --- | --- | --- |
| 初期化完了、まだ公開開始前（`open`） | 署名検証・読込み確認・候補の同期まではstage内で行う。世代IDと候補記録を耐久保存してから、候補と署名確認記録を世代側へ移し、移動元と移動先の親を同期する。 | 移動前はstageの規則に従う。移動後は、`open` で参照の不在と選択対象の記録を照合できた場合に限り候補になる。 |
| 切替開始を耐久保存（`switch_started`） | 公開ロック下で参照の不在と記録の整合を再確認し、対象IDを伴う切替開始を保存・同期・読み戻しする。その後にだけ `current.json` の書き込みを開始できる。 | この段階に達した保存先で参照が無い場合は、対象を含め今回の選択整理を保留する。開始記録の同期失敗で書き込みを見送った場合も、状態を戻す推測は行わない。 |
| 公開確認済み（`published`） | `current.json` の置換・同期・読み戻しに成功してから完了記録を耐久保存する。以後も完了記録を残す。 | 正常な参照がある場合はこれを唯一の現行参照とする。完了記録を保存する前の停止後に参照が見える場合も削除対象にはならない。後で参照が無くなれば履歴喪失として保全する。 |

切替開始後に参照が読めない場合、壊れている場合、参照が無い場合は、記録の巻き戻し、自動昇格、公開履歴の再構成を行わない。通常更新による同じパスへの上書きも保留する。`open` で参照が見つかるなど、記録と参照が矛盾する場合も保留する。対象外の不明な項目は保全し、他の候補の根拠に使わない。

### 4枠の事前確保と解除条件

現行の容量計上と同じく、世代ディレクトリと `stage-*` は別々の1枠とする。候補をできるだけ長くstage内に置いても、移動後はstageが残るため、初回の更新は**空き2枠**を確保できる場合に開始する。枠と既存の空きバイトの条件は、新しい待機記録の書き込み・freshclam起動より前に確認する。4枠使用中なら、初回更新のために整理が必要な場合は候補を1件ずつ選ぶ。1件整理後の3枠使用は「1枠確保」であり、残る1枠を確保できるまで更新可能とは案内しない。

一覧は実使用枠数・上限・初回更新の必要枠数を表示する。未認識のstageと来歴不明の世代も計上する。記録だけの通常の候補は別枠に数えない。削除処理が始まり、ディレクトリが消えたものの親の同期が未確認の場合は、その1枠を確保済みとして再利用しない。同期を確認して削除を確定した時点で解放する。世代の外へファイルを移すことや、容量超過を許す強制オプションは設けない。

例えば、切替開始前に止まった2回分のstageと配置済み候補が計4枠を使う場合は、候補だけを2回の選択操作で整理できる。残るstageや2回目の待機はそのまま保持し、空きができた後も通常の期限と復旧条件を満たすまで次の更新を開始しない。

来歴不明の世代が混在する場合は、根拠のある候補だけを整理できる。空き枠が足りても、不明な世代が残っている間は同じ保存先への初回公開を保留する。4枠すべてが来歴不明なら枠も解放できない。不明な世代が1件でも残る場合の対応は、空き枠の有無にかかわらず保存先全体の保全と調査とし、安全な新規保存先を検討できるのは、配布元が指示したものを含む既存の待機期限をすべて確認し、自然に経過した後とする。

### 所有者CLIでの選択整理

1. `clamav-signature-store list` は既存の一覧に、`unpublished_before_first_switch` と判定した世代のID・リビジョン・削除可否を示す。来歴不明、切替開始済み、読取不可、使用中の項目には保留理由を示す。候補のリビジョンは、保存先IDと公開記録、参照の不在、対象の内容・同一性、署名確認記録の状態、リース、待機・配布元同期の確認結果に結び付ける。
2. `clamav-signature-store delete GENERATION_ID --revision ENTRY_REVISION` で1世代を指定する。更新ロック下で判定とリビジョンを再検証し、公開ロックを短時間だけ取り参照がまだ無いことを再確認する。CVDのハッシュ照合は公開ロックの外で行う。使用を示すリースや対象の変更、読取・権限エラー、時間超過があれば保留する。名前で指定できるのは管理対象の世代IDだけとする。
3. 書き込み可能な対象は選んだ世代と対応する署名確認記録、および選択整理の進行記録に限る。署名確認記録が存在すればハッシュを照合する。移動の途中で署名確認記録がまだ移っていない場合も、完全なCVDと配置前の耐久記録を照合できれば対象にできる。親を同期し、対象の不在と対象IDの記録更新を読み戻した段階で完了とする。
4. 最初の削除前に `deleting` と検証済みの対象範囲を耐久保存する。途中失敗は `partial` とし、世代ディレクトリの不在を確認した場合だけ削除済みIDを返す。新しい一覧とリビジョンで、記録と一致する残りだけを再試行する。内容・型・同一性が確認できない残存物や追加されたファイルがあれば保留し、他の候補へ処理を広げない。

配布元同期が参照するstageと未復旧のstageはこの経路の対象外。待機中でも、根拠がそろった独立した世代の整理だけはできる。待機や配布元状態が読めない場合は保留する。整理は `attempt.json` の `pending`・期限、配布元正本・同期記録を変更せず、取得・公開・通常の `recover` を起動しない。再取得は通常の期限と所有者による復旧に従う。MCPへの変更操作の公開は行わない。

## 手作業での調査を維持する範囲

壊れた公開参照、根拠が不足した配布元状態、許可外のstageは保存先・同期記録・ログを一組で保全する。残った定義の版やファイル日時を根拠に現行を選び直したり、待機ファイルを削除・短縮したりしない。同期や所有者を確認できない場合は削除を止める。更新と整理は所有者向けローカルCLIに限り、MCPは読み取り専用の定義確認を維持する。

過去の `.cld` 入りstageは[試験限定の保全方針](clamav-preserved-stage-recovery-design.md)に従う。凍結原本・配布元同期・既存待機は維持し、429の元の記録は6件成功・2件未完了のままとする。別の追試は元の結果とは別に扱う。

## 実装後の確認

- 合成保存先でリース除去・親ディレクトリ同期・公開履歴書き込み・読み戻しをそれぞれ失敗させ、一覧からやり直せることを確認する。使用中、古いリビジョン、別ID、リンク、他ユーザー所有、ACL不備、現在の参照が変わった場合は拒否する。
- 優先2では、候補記録の保存前後、世代と署名確認記録の各移動前後、切替開始記録の同期失敗、参照置換後の同期・読み戻し失敗をそれぞれ検証する。正当な再起動と、参照が無い旧保存先・公開後に参照を失った保存先・記録の破損や差し替えを対照にする。
- 4枠から選んだ1件ずつだけ整理し、3枠では新規待機や通信を始めず、2枠で容量条件を満たすことを確認する。不明な世代が混ざる場合の初回公開拒否（新形式・旧形式とも、待機記録の書き込み・freshclam起動の前）、同期未確認時の枠保持、途中失敗後の再試行、使用中・古いリビジョン・リンク・権限不備の拒否、待機と配布元状態の不変を確認する。
- macOSとLinuxの専用試験保存先で、一覧・選択整理が30秒の処理枠に収まり、照合中に現行世代で検査を開始できることを確かめる。現行・使用中・最後の正常な過去世代が保護されることも確認する。
