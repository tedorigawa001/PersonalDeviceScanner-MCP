# 未対応の定義出力を残したstageの保全復旧案

2026-11-10作成。**設計案であり、例外付き復旧は未実装・未実行**。
[読み取り専用の調査記録](acceptance/clamav-cld-stage-investigation-2026-11-10.json)と
[429期限後復旧の受入記録](acceptance/freshclam-429-recovery-linux-2026-11-10.json)に基づく。
既存の[定義更新設計](clamav-signature-update-design.md)のCVD限定・待機保持・所有者CLI限定を維持する。
429再試行の集計は引き続き**6件成功・2件未完了**とする。

**現在の標準設定では、今回と同じ状態は通常想定しない**。現在の実装が生成するfreshclam設定は
`DatabaseMirror database.clamav.net` と `ScriptedUpdates no` に固定し、独自の配布元は指定しない。
承認した公式freshclamを設定を書き換えずに使い、差分更新によるCLDの組み立てを使わない通常経路を前提とする。
今回の `.cld` は、試験用アダプターが配布元を差し替え、試験の配信がCVDを `.cld` 名で返したことによる。
想定外の出力が残った場合に、現在の保護で停止して所有者の調査を求める動作は意図どおりである。
製品にこの例外経路を実装するか、試験の保存先だけを試験専用の記録した手順で扱うかは未決とする。
試験系の不備を別枠で集計する場合も、元の8件の**6件成功・2件未完了**の受入履歴を維持し、対象範囲の変更は新しい集計で明示する。

## 現在復旧できない理由

[signature_maintenance.tree](../pc_scanner/signature_maintenance.py)は管理可能なファイル名を限定しており、
`daily.cld`はその範囲に入らない。安全な権限の合成構造でも`Unknown signature maintenance entry`を再現した。
このため一覧では当該stageが`unavailable`・削除不可となる。

`recover`は期限経過を確認した後にも、`unavailable`が1件でもあれば拒否する。
現在の待機が自然に明けても、このstageがそのままなら通常の復旧は通らない。
これは名前の制限と検証不能時の保護によるもので、今回の調査で権限不備や署名破損を確認したものではない。

最短の確認期限は次のとおり。実施時には保存状態と配布元の追加指示を再確認する。

| 保存先の識別名 | 秒切上げした最短時刻（日本時間） | 期限後の条件 |
| --- | --- | --- |
| http-seconds | 2026-11-11 23:08:05 | 保全した未対応stageを扱う手順の実装・検証・所有者確認が必要 |
| http-seconds-cached | 2026-11-11 23:10:06 | 通常の所有者CLI復旧手順。こちらは未対応CLDを残していない |

## 方針

stageを元の場所に保持し、待機・配布元同期との参照関係と世代上限への計上を保つ。
既知の狭い構造について読み取り検証を追加し、**所有者がIDと検証revisionを明示したときだけ**、
そのstageを保護したままpendingを解除できる経路を設ける。

更新・公開で受け入れる定義は引き続き通常名の3つのCVDだけとする。
当該`.cld`をリネーム・現行世代へ移動・採用する工程は設けない。
原本からのstage退避、ジャーナルの書換え、待機情報の削除による回避も行わない。
一般の未知ファイル、署名確認不能なCLD、構造不明のstageは保護を続ける。

### 読み取り検証の範囲

将来の所有者CLIに、選択したstageの確認機能を追加する。仮の名前は`inspect-stage`で、現在は実行できない。
MCPには公開しない。

- 読取り時は既存ロックの競合を確認する。ロックやleaseがなければ作成して補わず、未確認を返す。
- dirfdとNOFOLLOW等で上位フォルダーから各ファイルまで確認する。現行の所有者・ACL・0700/0600・nlink条件、
  リンク・特殊ファイル・クラウド未取得拒否、深さ・項目数・総バイト数・時間上限を維持する。
- 第1対象は今回の構造だけとする。topはdb・空candidate・freshclam.conf、dbはmain.cvd・bytecode.cvd・daily.cld・freshclam.dat。
  不明な追加物や途中状態を自動で整理して検証可能にしない。
- CVDヘッダーを持つ3定義について、原本のハッシュと読取り前後の属性を確認する。
  私有の作業領域へ通常の独立ファイルとしてコピーし、`.cvd`名で所有者が承認したsigtoolを使う。
  コピーのハッシュ一致、署名行、終了0、Verification OKをすべて要求する。
- sigtoolだけを時間・出力上限付きで起動する。freshclam・clamscan・外部通信・DB読込み検査は行わない。
  作業領域は原本と別の0700/0600領域とし、空き容量不足や検証失敗は未確認として終了する。
- provider.dat、provider-sync.json、元stageのfreshclam.datはバイナリを解析せずハッシュで結ぶ。
  同期がpending、保存元が欠落、正本と不一致、参照が曖昧な場合はこの例外経路を使わない。
- 結果はstage ID、構造・定義版・ハッシュ・検証結果・未確認理由と確認revisionを返す。
  revisionにはstageの全項目、current、attempt、同期ジャーナル、正本と保存元providerのハッシュを含める。
  署名検証済みの表示と「更新・安全性の確認ではない」を併記する。

原本は読み取り専用とし、解析用コピーの作成・削除は別の作業領域だけで行う。
出力されたrevisionや所有者向け記録は、それだけで信頼できる許可証とはしない。

### 例外付き所有者復旧

通常の`recover`は現行の保守的な挙動を維持する。将来、例えば次の追加指定を設ける。
これは**未実装の引数案**であり、現在実行する手順ではない。

`recover --revision <一覧のrevision> --not-before <確認した期限> --acknowledge-preserved-stage <ID> --stage-review <確認revision>`

1. 更新ロックを取り、pending、current、全stage、同期ジャーナルと正本providerを取り直す。
   指定された全体revisionとstageの確認revisionに変化があれば中止する。
2. 所有者が確認した期限と全ての保存済み待機を比較する。期限前・短縮指定は従来どおり拒否し、
   独自の時刻変更・プロバイダー状態の初期化を使わない。
3. 選択したstageだけを上記の狭い検証で再確認する。読取り・コピー・sigtool検証の時間上限を含めて守る。
   確認revisionは一致だけで済ませず、署名検証と原本の不変確認も再度行う。
4. 他の`unavailable`、署名不明、ACL不明、provider同期不明があれば復旧しない。
   対象stageの「検証済みで保護する未対応出力」という理由だけを、所有者確認で受け入れる。
5. 成功時に限り、attempt.jsonのpendingをfalseへ安全に置換・同期する。next_attemptは短縮せず、
   元のstage・CVD・current・provider.dat・provider-sync.json・元履歴を変更しない。
   書込み結果が曖昧なら成功を推測せず、復旧状態を未確認として再読取りを要求する。

この例外経路でも、取得・検査用エンジン（freshclam/clamscan）の起動は0回とする。
追加される読み取り専用sigtoolの起動数は別に報告する。通常経路の外部コマンド起動0回は維持する。
復旧によって当該stageを削除可能にはせず、保護理由と容量への計上を維持する。

## 実装・検証後に実施する手順

1. 当該保存先で更新処理が動いていないこと、原本と今回の調査manifestが一致することを確認する。
   currentと旧正常世代、元429stage、未対応stage、待機、配布元正本と同期先を記録する。
2. 期限が自然に経過し、追加の配布元待機がないことを確認する。1件目は例外付き検証・所有者確認、
   2件目は通常の所有者復旧を使う。時刻を過去へ合わせたり待機を消したりしない。
3. CVDだけを返す正常なローカル配布元を独立保存先で先に検証する。
   `.cld`はヘッダー要求を含めて404、`daily.cvd`等の必要なCVDだけを206/200で返す。
4. 復旧した各保存先で実freshclamを1回だけ実行する。正本providerがそのまま渡り、署名検証・読込み・公開を通ること、
   旧世代・元429stage・未対応stageが不変であることを確認する。再失敗なら新しい待機を保持して停止する。
5. 合成対象の新定義での再検査、その次の再利用、二重計上なし、権限、ロック解放、子プロセス回収を確認する。
   成功が実確認できるまで「6件成功・2件未完了」を変更しない。

1件目は現在、旧世代1・stage2で上限4枠のうち3枠を使っている。正常更新で新世代を残すと4枠になる。
保全中stageを数から外したり、自動削除して次の更新を通したりしない。以後の整理は別の所有者判断とする。

## 実装前に必要な試験

| 条件 | 必要な結果 |
| --- | --- |
| 名前だけ.cldの署名付きCVD・今回と同一構造 | 明示確認と期限後だけpending解除。元stage・正本・参照は不変 |
| 通常のCLD、偽ヘッダー、署名欠落・破損、追加ファイル | 未確認を維持し、復旧・採用・削除を拒否 |
| 正常・改変したCVDの拡張子違い | metadata表示と署名確認を分離し、改変複製を拒否 |
| 期限の1マイクロ秒前・ちょうど・1マイクロ秒後、短縮指定 | 独立した合成fixtureで境界を検証。実保存先の時計・期限は変えない |
| stale revision、検証中の内容変更、リンク・所有者・ACL変更 | 解除前に拒否。旧定義・待機・配布元を保持 |
| provider同期pending・正本不一致・保存元欠落 | 例外確認で通さず、既存の復旧調査へ戻す |
| sigtool失敗・時間切れ・キャンセル・コピー容量不足 | 子を回収し、pendingを解除しない |
| attempt置換・fsync・再読取り失敗 | 成功を推測せず、不明状態と次の確認方法を返す |
| 明示指定なし・別stage ID・他のunavailableあり | 現行の保護を維持 |
| 復旧後の一覧・容量判定 | 未対応stageは保護されたまま1枠。現行・使用中・最後の正常な過去世代も保護 |

**未決事項：復旧後の当該stageの扱い**。上記のままでは、復旧後も当該stageは一覧で `unavailable`・削除不可のまま、
上限4枠のうち1枠を使い続ける。この保存先で以後の更新が失敗すると、通常の `recover` は再びこのstageで止まり、
毎回この例外経路が必要になる。実装する場合は、確認済みの構造に限ってCLIでの削除を認めるなど、最終的な整理方法を実装前に決める。

回帰試験、Android・実MCP SDKを含む全テスト、npmの通し試験と、別の合成stageによる実sigtool確認を実装後に行う。
その後に実保存先での期限後受入へ進む。今回の調査だけでは、この例外経路の実装完了・復旧成功とはしない。

## 今回の読取り証拠の限界

停止コンテナのTARから、内容・モード・UID/GID・パス構造・秒精度のmtimeを調査前後で比較した。
TARに現在のinode・ctime・nlink・ACLの完全な情報は含まれず、atimeも比較していない。
実操作時には原本のdescriptorに基づく検証が別途必要である。
今回、元の2保存先・待機・stage・配布元の変更や、例外付き復旧の試行は行っていない。
